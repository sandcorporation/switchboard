# Switchboard

Switchboard is a small self hosted mailbox for stable, role addressed agent identities. The service owns the identity boundary and durable message store; identities such as `sandcorp/boss` or `codemit/worker-1` are configured roles, not Orca session or terminal handles. A role keeps the same inbox after an agent session restarts.

Why we built it: [A role mailbox for AI sessions](https://sandcorp.co.kr/blog/role-mailbox-for-ai-sessions). Made by [Sandcorp](https://sandcorp.co.kr).

## Design decisions

- Go service and CLI share one module; SQLite is local to the service and persisted on a named Docker volume. SQLite keeps deployment small and avoids a separate database service.
- Every API call uses a bearer credential mapped server side to exactly one role. Existing `SWITCHBOARD_TOKENS=role=token,...` deployments are imported into SQLite at startup. New roles can enroll at runtime when the operator sets an external `SWITCHBOARD_ENROLLMENT_TOKEN`; senders cannot impersonate another sender, and recipients must be registered roles.
- The dashboard is an administrator view of all roles and mailboxes. Its only writes are question and permission answers, question settings and role revokes. It uses same-origin requests and never receives role credentials; message and question content is rendered as text.
- Watch is durable long polling. The cursor is the last delivered global message ID. Multiple watchers can replay from the same cursor and receive duplicate notifications; consumers should deduplicate by message ID. A watch only reports new mail; it does not mark mail read or wake a stopped LLM.

## Message and status semantics

Messages have sender, recipient, subject, markdown or plain text body, UTC timestamp, optional task ID, thread ID, and reply-to ID, and a priority: `normal` (the default) or `urgent`. Any role may send urgent mail; priority changes how mail is shown and streamed (urgent event frames include the body), not who may read it. The server stores urgent bodies in full; clients that show them inline choose their own length limit. New recipient messages are `pending`. Opening with `read` marks the message `read`; `ack` explicitly accepts responsibility and stores `acknowledged`; `complete` records finished work. These are recipient-side states. Inbox listing and watch do not consume or mutate messages. Outbox lists messages authored by the current role. Search matches subject, body, and task ID. Listing returns the newest 100 by default; `limit` (1–500) and `before` (only IDs below it) page it, and the CLI takes `--limit` and `--before` on `inbox` and `outbox`.

A role's send or reply to a base name (`<base>`, slot 1's mailbox) while two or more slots of that base are live is refused (#364): 409 `{"error":"ambiguous_recipient","message","recipient","live_slots":[{"role","machine","directory","label"}]}`, nothing stored. Name the session instead: `<base>-1` is slot 1 and goes, as does `<base>-N`. A reply to mail slot 1 sent (its sender is `<base>`) goes, an idempotent retry of mail stored before is answered as then, and system mail is never refused (it goes to slot 1 as before; a hosting scheduled run's mail goes to the record's own session, see ARCHITECTURE.md). Live is a lease that has not ended, as for `recipient_state`. `switchboard send` and `reply` print `보내지 않음: <base> 에 산 슬롯이 N개다. 슬롯 이름으로 골라라 (1번은 <base>-1)` and one line per live slot (`<role>  <machine>  <folder>  라벨 <label>`) on stderr and exit 1; `--json` prints the 409 body on stdout as well.

Mail to a mailbox with no live session waits for one of two things (#354). A mailbox (`<base>` is slot 1, `<base>-N` slot N) whose last session's lease has ended holds the mail for that session: the mail leaves the inbox (status `held`, `addressed_to` the mailbox) and goes to the next session of the base that is the same machine and folder (a session-marked folder `<folder> #<8 hex>` counts as the folder) or carries the same non-empty label, under a new ID; the next session that merely gets the number does not see it. The ID the sender was given stays reachable (#392): `GET /api/messages/{id}` and its `reply`, `ack`, `complete`, `read`, `close` and `withdraw` (also `/api/admin/messages/{id}/close` and `send --complete`) follow it to the ID the mail has now and check access on that mail (another role still gets 404); the answer carries the new `id` and `held_id`, the sent ID, which a second hand-off keeps. An ID the mail had between two hand-offs does not resolve. Without `--json` (and on stderr with it, stdout unchanged) the CLI prints `#<old> → #<new>(넘겨지며 번호가 바뀜)` when it asked by the old ID, and `inbox`, `outbox` and `read` show `#<new> (옛 #<old>) <subject>`. The same happens to unread mail a role sent when the session's lease ends (system mail stays, except answers, which were already handed off this way). The sender gets one system mail `[미수신] <mailbox> 받는 세션 없음 — #<id> <subject>` (idempotency key `handoff-held:<id>`), whose body ends `세션에 넘겨질 때 새 번호를 받는다. 옛 번호로도 찾을 수 있다.`. Held mail that nobody takes within `SWITCHBOARD_HANDOFF_EXPIRE` (Go duration, default `168h`) is marked `complete` where it is held (kept, never delivered) and its sender gets `[미수신] #<id> 끝냄 — <mailbox> 받는 세션 없음` (key `handoff-expired:<id>`). A mailbox that never had a session keeps its mail in the inbox for the first session that gets it. The send and reply responses carry `recipient_state` (`mailbox`, `live`, `ended_s` seconds since its last session ended, `held`, and `live_slots`: for mail to a base whose slot 1 has no session, the live `<base>-N` mailboxes) next to `no_session` (no live slot of the base, #300). `switchboard send` and `reply` print on stderr (exit code unchanged): nothing when a session reads the mailbox; `받는 세션 없음: <mailbox>, 마지막 세션 N분 전 끝남. 붙잡아 둠` when the mail was held; `<base>-2, <base>-3 이 살아 있음. 그 슬롯 이름으로 보내라` when slot 1 is empty and other numbers are live; otherwise `send` prints `no session of <role> is attached; the mail waits in its inbox`. The sweep also tells the sender once about mail still pending in a mailbox no session reads: when that mailbox (its slot number) has no live session, none left it within the last 5 minutes, and the sender's oldest pending mail to it is 5 minutes old, it sends a system mail `[미수신] <mailbox> 붙은 세션 없음 — #N 외 M통` (once per stretch, keyed on the mailbox and the oldest pending message; a mailbox that never had a session gets it too).

A thread's root ID is shared in `thread_id`; `reply_to` points at the immediate parent. Idempotency keys are unique per sender and key. A retry with the same key returns the original message and does not create a second one. Keep a key stable for retries of one logical send and use a fresh key for a new message.

## Directives

```
          sent              read                 done
 [sent] ──────▶ [delivered] ──────▶ [open] ───────────────▶ [done]
                                    ▲   │
                                    └───┘
                          replies (any number, state unchanged)
```

- Directive: mail from a boss role that carries work: a send, or a reply sent with `--directive`. Mail sent with `--no-reply` is never one.
- Reply: mail back from a role of the recipient's base to the sender's base, `reply_to` the directive or in its thread. A reply, however many, leaves the directive open: "started" and the final report are both replies.
- Done: the recipient ends the directive with `switchboard reply ID --complete` (the final report and the complete mark in one transaction; `--done` is the older name) or `switchboard complete ID`. The same works for any mail, not only a directive: `reply ID --complete` completes the mail it answers, `send --complete ID[,ID...]` completes mail the sender received with the send, and `report --mail ID` completes the linked mail the reporter received.
- Close: the sender ends it with `switchboard close ID` (it stores `no_reply`; a directive its recipient has not read or answered is withdrawn as well, see Withdraw), or with `switchboard close ANSWER` given the ID of an answer it received, which also completes that answer.
- Left (#470): an answer that ends a directive says what it left undone. The answers that end one are `reply N --complete` (and `send --complete N`) by its recipient, `complete N` by its recipient while N has not ended, and `close N` by its sender while N has not ended (the closer says). They take `--left "ITEM"` (repeatable) or `--left-none`; this CLI sends `X-Switchboard-Left: 1` and the server refuses its ending answer with neither (or both). An older CLI's ending answer is taken and leaves an open "unrecorded" item instead. Acknowledgements, progress replies and the complete of mail that is not a directive ask nothing. A send is not a directive when its recipient has an open directive to the sender's base under the same non-empty task ID (#480): a worker's "PR opened" notice is a report, so the receiver's `complete` asks nothing and the progress view does not count it. Each item stays open in 진행 대기 until the directive's sender raises it as an issue (`left issue ID URL`) or passes it on in a directive it sent (`left pass ID --directive M`), or a signed-in admin drops it with a reason on the dashboard (no CLI). `left add N TEXT` adds an item found later to a directive the caller ended. The sender may also give `--left` (or `--left-none`) to `complete A` of an answer A it received to its directive (#483): it ends the directive while open, as `close A` does, and adds the items to its ledger once it has ended. Elsewhere `--left` on `complete` is refused, and the refusal names the command to give instead with its numbers filled in.
- Open: delivered or read and neither done nor closed. Progress (열린 지시), 대기, the reminders, the idle check and the 보고 status all read this one state (`mail.AnsweredRule.Open`, answered rule version 2).
- The sender sees it too. When a mail is a reply (under the answered rule) in the thread of a directive the reader sent, `read`, `inbox --json`, `watch`, `/api/events` and `/api/events/poll` carry `"answers_directive":{"id":N,"state":"open"|"done"}`. The directive is the nearest one up the reply chain (the replied-to mail, else what it replied to, up to the thread root); `state` is `open` while `mail.AnsweredRule.Open` holds. The directive's recipient, and anyone else, never gets the field. Text `read` (and `inbox`) prints `directive #N still open: close M closes it and completes #M` (M the answer) under the header while it is open, and nothing once it is done or closed. Text `read` by the recipient of mail that is not complete (and no such answer) prints `reply ID --complete answers and completes; complete ID ends it without an answer` on stderr.

## Build and run locally

On a machine without Go, run `scripts/go <go args>` (for example `scripts/go test ./...`): it uses docker (a local image of the Go toolchain plus tmux, built on first use, so `SWITCHBOARD_TEST_TMUX=require` runs the tmux tests without a skip) and keeps the Go caches in `~/.cache/switchboard-go` (`SWITCHBOARD_GO_CACHE` overrides; under `/tmp` or on tmpfs it refuses). `bash scripts/go_test.sh` tests the script and the hook in `.claude/settings.json` that blocks hand-written `golang` containers and `/tmp` Go caches.

Requires Go 1.25+ for development. End users install a compiled release binary and do not need Go. Create distinct random tokens per role and set them in the environment (never commit token values):

```sh
export SWITCHBOARD_TOKENS='sandcorp/boss=REPLACE_WITH_RANDOM,codemit/coordinator=REPLACE_WITH_RANDOM,codemit/worker-1=REPLACE_WITH_RANDOM'
export DB_PATH="$PWD/mail.db"
go run ./cmd/switchboard
```

The service listens on `:8080` by default. Visit `http://localhost:8080`. Health endpoint: `/health`.

Configure a CLI (read the token from a protected file; the token is stored with user-only file permissions):

```sh
switchboard config set --endpoint http://localhost:8080 --role codemit/worker-1 --token-file /path/to/role-token
switchboard --profile codemit-worker config set --endpoint http://localhost:8080 --role codemit/worker-1 --token-file /path/to/role-token
switchboard send --to codemit/coordinator --subject 'Build ready' --task task-123 --body-file report.md --idempotency-key task-123-report
cat report.md | switchboard send --to codemit/coordinator --subject 'Build ready' --body-file /dev/stdin
switchboard inbox [--q term] [--status pending|read|acknowledged|complete] [--of ROLE] [--json]
switchboard outbox --json
switchboard read 42
switchboard reply 42 --subject 'Re: Build ready' --body 'Thanks'
switchboard reply 42 --complete --left-none --body 'Built and deployed'
switchboard reply 42 --complete --left 'rename the files' --left 'per-login permissions' --body 'Built; two things left'
switchboard send --to codemit/coordinator --subject 'Done' --complete 42,43 --body 'Both handled'
switchboard send --to codemit/coordinator --subject 'Deploy blocked' --body 'Needs a decision' --urgent
switchboard ack 42
switchboard complete 42 --left-none
switchboard close 41 --left-none [--json]
switchboard close 44 --left-none   # 44 answers directive 41: closes 41 and completes 44
switchboard complete 44 --left 'docs'   # the same, or adds to 41's ledger once 41 has ended
switchboard left add 42 'found later'     # to a directive you ended
switchboard left issue 7 https://example.com/issues/12   # sender of the directive item 7 came from
switchboard left pass 7 --directive 45                   # a directive the same sender sent
switchboard search 'cache ttl'                           # mail, reports, questions, left items: newest 50, two lines each
switchboard search 'ttl\s+\d+' --regex --case --kind mail --role team/worker --since 2026-10-01 [--after CURSOR] [--json]
switchboard withdraw 43 [--json]   # take back mail the recipient has not read
switchboard watch --after 0 --json
switchboard wait --timeout 1800
switchboard events --after 41 --timeout 25
```

Every dashboard API has a CLI command (#399). When you add a screen or an action to the dashboard, add its call and the command that does the same to the pair table, `internal/dashboard/cli_pairs.go`; `TestCLIPairs` fails on a call without a row, a command the CLI does not take, or an exception without its reason.

Write rules: a global boss (`SWITCHBOARD_BOSS_ROLES`) makes the dashboard admin's writes at `/api/boss/<admin path>` (the same handlers); a group's `boss_role` only on targets of its group (a session, job, schedule, role or mail of the group, a `PREFIX/*` setting of it), and 403 on the server-wide ones (the subscription limit, nodes, the `*` and ungrouped question settings); any other role gets 403. Admin accounts (`admin create`, `passwd`, `totp-reset`, `disable`, `enable`, `list`) stay in the server container. Every write is recorded in `boss_writes` and the log (role, method, path, target, status; never the request body). A write that is hard to undo (`--yes` above) prints one line saying what it would do and exits 2 without `--yes`. No dashboard write takes a secret today; one that does reads it from stdin, never an argument, and never prints or records it. Exceptions without a command, each with its reason in the table: the page's sign-in check (`me`), the terminal view's ticket and socket, and the live change bus.

`switchboard inbox` prints:

```text
#42 Build ready
team/worker → team/boss · complete
  Tests pass.
  #41 is fixed too.
```

`send` and `reply` accept `--body`, `--body-file`, or piped stdin. `--urgent` sends with priority `urgent` (without it the request carries no priority field, so older servers accept it unchanged; an older server ignores `--urgent` and stores normal mail). `reply` without `--subject` uses `Re: ` and the replied-to subject. `reply --complete` (older name `--done`) sends the final word and marks the replied-to mail complete in one transaction, directive or not; a plain `reply` to a directive leaves it open and prints `directive #ID stays open: complete ID ends it (or next time reply ID --complete)` on stderr (`--json` output has `directive_state`, `open` or `done`). `reply --idempotency-key KEY` makes a retry return the first reply without storing or marking anything twice. `send --complete ID[,ID...]` (repeatable; the request's `complete` array) marks mail the sender received complete in the send's transaction; an ID that does not exist (404) or was not sent to the sender (400) refuses the send and stores nothing, and a retry with the same idempotency key returns the first message and marks nothing again. `reply --directive` marks a reply that carries new work, so `progress` lists it as an open directive (a plain reply, such as an acknowledgement, is not one; without the flag the request carries no `directive` field). `send --no-reply` and `reply --no-reply` store the mail as needing no answer (`no_reply` in `--json` output): it is never an open directive in `progress` and never reminded (without the flag the request carries no `no_reply` field). Human-readable `inbox`, `outbox` and `read` output prefix urgent subjects with `[urgent]`; each message is a header line `#ID subject`, a `sender → recipient · status` line and the body with every line indented by two spaces, so only header lines match `^#\d+` even when a body line starts with `#123`. The status is the recipient's, the same for sender and recipient in `read`, `inbox` and `outbox`; `--json` output includes `priority`. `--json` returns machine-readable results for list/read/send/status operations. `watch` is a reconnecting long poll; save its printed cursor and pass it back with `--after` after restarting. A `watch` line for an answer to an open directive the role sent reads `New message #M (cursor C): answers directive #N, still open`; `watch --json` lines are `{"message_id":M,"cursor":C,"answers_directive"?:{"id":N,"state":"open"|"done"}}`. Notifications can repeat after reconnect by design.

A boss role (`SWITCHBOARD_BOSS_ROLES`) can view another mailbox read-only: `switchboard inbox --of ROLE` (`GET /api/messages?of=ROLE`, ROLE a role or slot) lists it and `switchboard read ID` opens mail of any role. Read and complete states do not change, `reply`, `ack`, `complete` and `close` are not widened, and any other role gets 403 for `--of`. The server marks such a response with `view_only: true` (each message of an `--of` list, or the one `read` returns; mail the caller's own mailbox holds, a slot-1 session's included, is never marked), and the CLI prints `다른 메일함 보기(상태 안 바뀜)` on stderr only for that field, so an older server that sends none prints no line. Each view (viewer, mailbox, message ID or 0 for a list, time) is appended to the `mailbox_views` table; bodies are not stored.

`wait` checks the inbox for `pending` messages (every `--interval` seconds, default 15), prints them as `#ID sender | subject | task=ID` lines (or a JSON array with `--json`; urgent lines end with ` | urgent`, normal lines are unchanged) and exits 0. It never marks anything read, and it returns immediately when pending mail already exists, so it is safe to run as a background "wake me when mail arrives" step. With no pending mail before `--timeout` (default 1800 seconds, `0` = no limit) it exits 3. Credential errors exit 1 at once; transient network errors are retried.

`events` makes one long-poll request to `/api/events/poll` and prints each event as a `#ID sender | subject | task=ID` line (urgent lines end with ` | urgent`, like `wait`), or the server's `{"events":[...],"cursor":N}` response unchanged with `--json`. `--after ID` resumes after a cursor (default: every pending message) and `--timeout SECONDS` sets the wait (default 25, `0` = answer at once, capped by the server). It exits 0 when events came back and 3 when none did (printing `no new mail (cursor N)` to stderr). It never changes message state.

Every command accepts only its own options; `switchboard <command> --help` lists them. An unknown command or option, a missing option value, or an invalid `--status` exits with code 2 instead of being ignored; stderr then ends with the reason (`switchboard: …`), after the `Run 'switchboard --help' for usage.` line. Exit codes: 0 success, 1 error, 2 usage error, 3 `wait` timed out or `events` returned no mail, 4 `node` stopped because the host refused its token (the node was revoked).

Use a separate `--profile NAME` for each local session or role; each profile has its own protected credential file. `--profile NAME` (or `--profile=NAME`) works before or after the command, including `config set`, and takes precedence over `SWITCHBOARD_PROFILE`. A profile named by either must already have a saved config; the CLI exits with an error rather than falling back to the default profile. `SWITCHBOARD_PROFILE`, `SWITCHBOARD_ENDPOINT`, `SWITCHBOARD_ROLE`, and `SWITCHBOARD_TOKEN` can select or override a profile for isolated process environments. **Numbered roles:** a session holding `team/worker-2` with a `team/worker` profile acts as that number with the global `--role team/worker-2` (before the command) or `SWITCHBOARD_ROLE=team/worker-2` (`--role` wins); the value must be the profile's role or `<profile role>-N`, otherwise the CLI exits with usage error 2. (When `SWITCHBOARD_TOKEN` is also set, or the profile has no saved role, `SWITCHBOARD_ROLE` is the role itself, as before.) The server keeps mailboxes of one base apart: reading, acknowledging, completing or replying to mail of `team/worker-2` while the header names `team/worker` or another number answers 403 naming the role to use; nothing is shown and no state changes. The server always derives the sender role from the credential, regardless of caller-supplied message fields. To enroll a role without restarting the server, set the operator-only enrollment credential in the deployment's external `.env`, then run `switchboard register --endpoint URL --role ROLE --token-file ROLE_TOKEN_FILE --enrollment-token-file ENROLLMENT_TOKEN_FILE`. A role owner can resume with the same role credential; registration cannot replace an existing role credential. Keep the enrollment credential private and rotate or remove it when enrollment is closed.

## Jobs

A command handed to switchboard keeps running when the session that started it restarts (Linux, macOS and Windows).

```sh
switchboard job run --wait --label build -- make build     # streams the output, exits with make's exit code
switchboard job run --expires 7d --idem nightly-1 -- ./sync.sh   # prints the job ID and returns
switchboard job list [--state running] [--owner team/worker] [--json]
switchboard job show ID | job tail ID [-f] | job stop ID | job wait ID
switchboard job ping [--json]                                # checks that a hand-over can work here
switchboard watch start --label app-log -- tail -F app.log     # prints the watch's job ID and returns
switchboard watch start --attach --batch 10s -- ./events.sh    # streams the lines while attached
```

- `job run [--wait] [--expires DURATION] [--no-extend] [--cwd DIR] [--label TEXT] [--idem KEY] -- CMD ARGS...` registers the job (`POST /api/jobs`) and starts a runner detached from the caller. The runner is never a child of the caller, so killing the waiting or attached client's process tree does not reach it. Linux: when a systemd user manager is reachable, the runner is a transient user unit of its own (`systemd-run --user --collect --unit switchboard-job-<ID>-<hash>`, named after the job folder, never the command), outside the caller's cgroup, so a terminal host stopping the terminal's systemd scope on close does not end it; otherwise, and on macOS, it is detached twice through `sh` into a session of its own (`setsid`). Stdin is `/dev/null`, the command in a process group of its own. Windows: outside the terminal's job object (`CREATE_BREAKAWAY_FROM_JOB`) on a hidden console of its own, the command in a job object and console process group of its own; the runner runs from a copy of the binary, `<config dir>/runner/switchboard-<version>-<hash>.exe`, so `switchboard.exe` can be replaced while jobs run, and each `job run` removes the older copies no runner still runs from. When no runner can start — on Windows the terminal's job object, or one around it, forbids breakaway (checked before anything is registered by starting the binary suspended with `CREATE_BREAKAWAY_FROM_JOB` and ending it), on Linux the caller runs in a systemd scope (`/proc/self/cgroup`) and no user manager is reachable to start the runner outside it, or the start fails — `job run` and `watch start` exit with code 125 and print `switchboard: job not handed over, run the command yourself: <reason>` on stderr; the caller (the plugin hook) then runs the command itself. The output goes to `<config dir>/jobs/<profile>/<ID>/output`, readable by the user only; finished jobs' folders are removed after 7 days. The label defaults to `명령 #<ID>` (never the command, #410), `--expires` to 24 h (`90m`, `24h`, `7d`). The same `--idem KEY` from the same role returns the first job and starts nothing.
- `--wait` prints `switchboard job <ID>` on stderr first, then streams the output and exits with the command's exit code (128+N when signal N ended it, 127 when it could not start). Killing the waiter leaves the job running; `job wait ID` reattaches from the start of the output and exits the same way. Without the local output (another machine) it waits on the server and prints the stored tail.
- At the end the server records the exit code, the end time and the last 50 lines (8 KB) of output. When no waiter saw the end, the owner role gets one mail, `[작업 끝남] <label> exit N` with the tail: normal for exit 0 or a stop, urgent otherwise.
- `watch start [--attach] [--expires DURATION] [--no-extend] [--batch DURATION] [--cwd DIR] [--label TEXT] [--idem KEY] -- CMD ARGS...` starts a job of kind `watch` (expiry 7 days by default) whose output lines are events. The runner collects the lines of a batch window (`--batch`, default 30 s, opened by the first line) and sends them as one batch (`POST /api/jobs/ID/lines`); the owner role gets one urgent mail per batch, `[감시] <label>: N줄`, with the first 50 lines (8 KB) and the count of the rest (idem `watch:<ID>:<batch>`). `--attach` prints `switchboard job <ID>` on stderr and streams the lines to stdout; while it is attached the runner sends no batch. Killing it leaves the watch running and the next batches go out as mail; `job wait ID` attaches again. The watch command's exit ends the watch (the last batch first) with the end mail. `--no-extend` (also on `job run` and `schedule add`) fixes the expiry: the presence sweep never moves it, so the watch or schedule ends at `--expires` even while a session of the role is attached, with the expiry mail. A plugin hook turns a Monitor call with a timeout into `watch start --attach --no-extend --expires <timeout>`. `job show`, `schedule show` and `--json` carry `extends` (false for a command job and for a row made with the flag). `watch` without `start` is still the inbox watch. List, stop and tail a watch with `job`.
- While a job runs, its runner reports to the server every 5 s, with the output tail when the output grew, so the dashboard shows its last line.
- Lost: a job whose runner is gone without an end (the machine rebooted, the runner was killed) becomes `lost`, with one urgent mail `[작업 끝남] <label> 잃음`. Each `job run` and `watch start` first reports which jobs have a live runner on this machine (`POST /api/jobs/machine`); the role's live jobs on that machine not among them and older than a minute become lost. A live job whose runner has not reported for 10 minutes becomes lost at the next sweep. A runner that reports again (the server was away) takes its job back, and its end is recorded and told as usual.
- `job stop ID` records the stop on the server and, on the job's machine, terminates the command's process group (killed after 5 s); the state becomes `stopped`. On Windows the runner reads the stop from the server within 5 s, sends CTRL_BREAK to the command's console process group, and after 5 s ends its job object: the command and every process it started. When a Windows command ends, whatever it left running in its job object ends with it. A runner also asks the server every 5 s whether the job was stopped (the dashboard, `job stop` from another machine) and when it expires, so those stops reach it too.
- Expiry: commands default to 24 h, watches to 7 days. At `expires_at` the runner terminates the command (killed after 5 s); the state becomes `expired` and the owner role gets one urgent mail, even when a waiter saw the end. While a session of the owner role is attached, each presence sweep moves a watch's expiry to now plus the duration it was created with; a command's expiry never moves. The last expiry the runner saw holds while the server is unreachable.
- The dashboard's 작업 tab (under 운영) lists every role's jobs with role and state filters (default: not ended), and stops a live job or removes an ended job's record after a confirm. The list shows labels only; opening a row shows the job's full command, cwd and machine, or a schedule's condition (cron or time, next fire, expiry) and full prompt. States: `handed`, `running`, then `exited`, `failed`, `stopped`, `expired` or `lost`.
- Only the owner role stops or reports on a job. `job list` shows a boss role the jobs of the roles in its scope (every role for a global boss), with the command only on its own; another role's command is read one job at a time (`jobs show ID`, the dashboard's opened row, `GET /api/jobs/ID` or `/api/admin/jobs/ID`) by the admin, a global boss, the group's boss for its group, and the owner. Each such read by anyone but the owner is recorded (`ledger_views`: who, which item, whose, when; never the text). No list API carries a command or a prompt for anyone but the owner. The server keeps the command text; the runner never logs it. Nothing sends a command to a machine: the runner reports up, and only a stop travels down.
- `job ping [--json]` answers within 1 s and registers nothing. It checks, in this order: the profile is configured, `<config dir>/jobs/<profile>` takes a file, the server answers `GET /api/whoami` within 0.8 s, the server accepts the role token, and a runner can leave the caller (Windows: the breakaway probe above; Linux: not in a systemd scope, or a user manager is reachable). Each check prints `<check> ok` on stdout or `<check>: <reason>` on stderr; `--json` prints `{"ok", "exit", "checks": [{"check", "ok", "error"}]}`. The exit code is the first failed check's:

| Exit | Check | Cause |
| --- | --- | --- |
| 0 | — | every check passed |
| 10 | `config` | the profile is missing or lacks endpoint, role or token |
| 11 | `data` | the data directory is not writable |
| 12 | `server` | no answer within 0.8 s, or an error status |
| 13 | `token` | the server refused the role token (401, 403) |
| 14 | `runner` | no runner can start here (Windows: breakaway refused; Linux: a systemd scope and no user manager) |

### Plugin hook contract

The Claude Code plugin hook hands background work to switchboard. Before each rewrite it runs `switchboard job ping`; any exit other than 0, a missing binary, or a version below v0.29.0 (the first with `job ping`; an older binary exits 2 on it) leaves the call unchanged, and the hook adds one line to the result saying the work was not handed over.

| Tool call | Hand-over |
| --- | --- |
| Bash with `run_in_background: true` | command rewritten to `switchboard job run --wait --label <first 60 characters> -- <shell> -c <command>` |
| Monitor with a timeout of T ms | command rewritten to `switchboard watch start --attach --no-extend --expires <T>ms --label <description> -- <shell> -c <command>` |
| Monitor without a timeout | command rewritten to `switchboard watch start --attach --label <description> -- <shell> -c <command>` |
| CronCreate | `switchboard schedule add --cron <expr> --prompt <prompt>`; the call is denied with a reason naming the schedule ID and saying fires come as mail |
| CronDelete | `switchboard schedule rm <ID>`, call denied with the result |
| CronList | `switchboard schedule list`, call denied with the list |
| ScheduleWakeup (delayed wake-up) | `switchboard schedule add --in <seconds>s --prompt <prompt>`; the call is denied with a reason naming the schedule ID |

- `<shell>` is the shell the tool would have run the command in.
- `job run --wait` and `watch start --attach` print `switchboard job <ID>` as the first stderr line. A restarted session reattaches with `switchboard job wait <ID>`; a watch nobody is attached to sends its lines as urgent mail.
- Exit 125 from `job run` or `watch start`: nothing was handed over and the command did not run (the stderr line says why).
- Slot register and heartbeat send `X-Switchboard-Version: <vX.Y.Z>`, the version `switchboard version` reports, read once per session; when the CLI is missing or does not answer, the header is left out.

## Schedules

A schedule is a prompt the server mails to the role at times. Nothing runs on the machine, so a schedule survives a session restart and a reboot of the machine.

```sh
switchboard schedule add --cron '*/30 9-18 * * 1-5' --label standup --prompt 'Check the build and report'
switchboard schedule add --in 20m --prompt 'Look at the deploy again'     # once
switchboard schedule add --at '2026-12-01 09:00' --prompt 'Release day'    # once, local time
switchboard schedule list [--state active] [--owner team/worker] [--json]
switchboard schedule show ID | schedule rm ID
switchboard schedule pause ID [--reason 'deploy freeze']
switchboard schedule resume ID [--fire | --drop]
```

- `schedule add (--cron EXPR | --at TIME | --in DURATION) [--expires DURATION] [--no-extend] [--label TEXT] [--idem KEY] --prompt TEXT` stores the schedule (`POST /api/schedules`) and prints its ID. `--cron` takes the standard five fields (minute, hour, day of month, month, day of week; `*`, values, ranges, lists, steps, `jan`-`dec`, `sun`-`sat`) read in the machine's time zone, recorded at creation (`$TZ`, else `/etc/localtime`; on Windows the current UTC offset). `--at` takes RFC 3339, `YYYY-MM-DD HH:MM` or `HH:MM` (today, or tomorrow when it has passed). The label defaults to `예약 #<ID>` (never the prompt, #410).
- The server sweep fires schedules. A fire while a session of the role is attached is one normal mail, `[주기] <label>` with the prompt as the body. A fire with no session attached is recorded as missed; the next sweep that finds a session attached sends one mail with the prompt and `밀린 N회, 마지막 <time>`. While a schedule's previous mail is unread, its next fires are counted the same way, so a schedule never has more than one unread mail. Each mail's idempotency key names the schedule and the fire, so a server restart sends no fire twice.
- A `once` schedule ends (`ended`) after its fire is delivered. Expiry defaults to 7 days and moves forward while a session of the role is attached, as for watches. At expiry the state becomes `expired` and the role gets one mail, `[주기 만료] <label>`, with any missed fires.
- `schedule rm ID` deletes it; only the owner role removes a schedule. `schedule list` shows a boss role the schedules of the roles in its scope, with the prompt only on its own; `schedule show ID` prints one schedule with its prompt for the owner, the admin and a boss role over it, and records the read as `jobs show` does. The dashboard's 작업 tab lists schedules with the jobs (without the prompt), opens one with its condition and prompt, and removes one after a confirm.
- `schedule pause ID [--reason TEXT]` pauses an active schedule (`POST /api/schedules/ID/pause`); the owner, the admin and a boss role over it may (the same rule as removing one, also at `/api/admin/schedules/ID/pause` and through `/api/boss/`). While paused the schedule sends nothing: the fire times that pass are dropped, not counted as missed, and its expiry clock stops — `schedule resume ID` (`POST …/resume`) moves `expires_at` on by the paused time and a cron schedule fires next at its first time after the resume. A once schedule whose time passed while paused shows `(time passed)` (지나감 on the dashboard) and resumes only with `--fire` (send the prompt now) or `--drop` (drop it; the schedule ends); without either the command exits 2 and the server answers 409. `schedule list`, `show` and the dashboard show who paused it (관리자 <name> or 역할 <address>), when and why; every pause and resume is kept in `schedule_pauses`. When anyone but the owner pauses or resumes, the owner gets one normal system mail, `[예약 멈춤] <label>` or `[예약 켬] <label>`, which needs no answer. The dashboard's opened schedule has 멈춤 and 다시 buttons.

## Docker deployment

The Compose file binds to loopback by default (`127.0.0.1:8097`). For private network access, set `MAIL_BIND_ADDRESS` in the external `.env` to the intended private interface address; do not bind publicly without a TLS reverse proxy and appropriate network controls. Set `SWITCHBOARD_TOKENS` and, when enabling dynamic enrollment, `SWITCHBOARD_ENROLLMENT_TOKEN` in an external `.env` file with mode `0600`; build and start with `docker compose up -d --build`. The enrollment value is optional so existing deployments continue to start; registration is disabled until it is set. Existing role definitions and message history stay in the SQLite volume. The container runs as nonroot, drops capabilities, has a read-only root filesystem, health check, restart policy, and a named volume. Never put credentials in the Compose file or source control.

### Automated deployment (Actions image + Jenkins)

`docker compose up -d --build` above builds locally (the image is tagged `switchboard:local`). The production path never builds on the server:

1. A pull request runs `CI` (tests, vet, build).
2. A push to `main` runs `promote`: the same checks in parallel with `image`, which builds a multi-arch image (`linux/amd64`, `linux/arm64`; Docker pulls the host's architecture) and pushes `ghcr.io/sandcorporation/switchboard:<commit sha>`, which the deployment pulls,. When both pass, `production` is fast-forwarded to that commit (`scripts/ci/promote.sh`). `production` only moves forward; roll back with a revert PR.
3. A Jenkins job using the `Jenkinsfile` watches `production` only. Through the `sandcorp` shared library (`sandcorpDeploy`) it waits for the GHCR image of the `production` head, pulls it on the node labelled `switchboard-deploy`, checks the settings with it (below), recreates the `switchboard` service with `SWITCHBOARD_IMAGE` set to that image (`--no-build`), waits for the container health check and runs `/health` inside the container. If the new container does not become healthy it switches back to the previous successfully deployed image. The `ROLLBACK_SHA` job parameter deploys an older published image (commits before #157 were published only under the old image name).

Nothing deploys until such a job exists. Host-specific values are not in this repository: the deploy node is chosen by its Jenkins label, and secrets plus `MAIL_BIND_ADDRESS` come from the `.env` file in the job workspace on that node (mode `0600`, same `SWITCHBOARD_*` keys as above), or, optionally, from an env file outside the workspace named by the node's `DEPLOY_ENV_FILE` environment variable. The workspace `.env` is the default; note that Jenkins can wipe the workspace when a checkout fails, so keep a copy of it. The first clone into a new workspace also empties it: put the `.env` there after the job's first run (which stops at the check below), then run the job again. The deploy stops before replacing anything if `SWITCHBOARD_TOKENS` or `MAIL_BIND_ADDRESS` is empty. Keep the Compose project name `switchboard` so the existing `switchboard_switchboard_data` volume is reused; moving from a manual deployment only recreates the container. The deploy node needs Docker with Compose and pull access to the GHCR package.

To change a setting, edit that `.env` and deploy once; the check stops a wrong setting. A plain run of the job skips a commit it already deployed (even with Build Now), so run it with the parameter `ROLLBACK_SHA` set to the commit `production` is at (`git rev-parse origin/production`): that deploys the same image again with the new `.env`. Such a run has no automatic rollback (its previous image is the same one), which is why the check runs first. Before the service is recreated, the deploy brings up the Compose service `switchboard-check` (the library's `preServices`) with the new image and the same `.env`. It runs `switchboard serve --check`: the server's own start-up decisions (admin login and OIDC, hosting, listener addresses, durations and thresholds) without opening the database or binding a listener. When the server would refuse to start, it prints each refused setting by name, never a value, and exits 1; the deploy then stops and the running container stays as it was. When `SWITCHBOARD_PUBLIC_URL` is set, the check also asks that address for `/health` (certificate checked) and prints a warning when no switchboard answers, without failing: on a first deploy the proxy may not exist yet. An image from before the check (a `ROLLBACK_SHA` to an older commit) is not checked. Locally: `docker compose run --rm --no-deps switchboard serve --check`.

### CI time, reuse and skips

| Run | Tests | Job time limits |
|---|---|---|
| Pull request | everything; a pull request that changes only `*.md` and `docs/**` skips the test steps and `test`, `windows` report green (`scripts/ci/docs_only.sh`) | `test` 10 min, `windows` 20 min |
| Push to `main` (`promote`) | reuses the pull request run when its head has the same git tree and `test`, `windows` ran their tests and passed (log line `재사용: run <id>`); otherwise runs `CI` again (`scripts/ci/reuse.sh check`) | `reuse` 5 min, `CI` as above, `promote` 5 min |
| Tag `v*` (`Release`) | skipped when the tagged commit has a successful `promote` run (`scripts/ci/reuse.sh release`); the six archives build in parallel | `test` 15 min, each build 10 min, `publish` 5 min |

Locally, `scripts/go-changed` tests only the packages a branch can reach: those with changed files since the merge base with `origin/main` (`--base REF`) and every package importing them, directly or through others, from code or tests (`go list -test -deps`); go.mod or go.sum tests `./...`; `--list` prints the packages. The full suite runs in CI.

Reuse is decided only from GitHub API values and git trees, never from files or text a pull request run produced; a fork, a different tree, a failed or docs-only run, or any API error means a full run. `go test` runs with `-timeout 8m` (Linux) and `12m` (Windows), and `scripts/ci/test_budget.sh` fails any single top-level test over 30 s on Linux or 60 s on Windows, except those listed in `scripts/ci/test_budget_allow.txt` with the issue that brings them under budget.

### Protected administrator dashboard

The dashboard shows all messages, sessions and registered role names, and lets the administrator answer questions and permission requests, edit question settings and revoke or restore roles. The 설정 tab has four views, each a list whose rows open the detail panel (`#settings/<kind>:<id>/<sub>`): 질문 설정 (`#settings`; 추가 in a drawer, edit and 삭제 in the detail), 역할 (`#settings-roles`; 끊기 / 되살리기, each behind a confirm), 노드 (`#settings-nodes`, hosting only; 끊기 behind a confirm) and 다시 알림 (`#settings-reminders`), which shows `GET /api/admin/settings` read-only: `{"version","hosting","reminders":{"on","after","after_seconds","max","since"}}`, `since` being the first sweep with reminders on (`null` before it). The response carries no token, webhook address or other secret. Who may use it is set by `SWITCHBOARD_ADMIN_AUTH`:

| `SWITCHBOARD_ADMIN_AUTH` | `SWITCHBOARD_ADMIN_PROXY_TOKEN` | Admin access |
|---|---|---|
| unset | unset | Denied (default). `/api/admin/*` returns `401`; the page is the login form, which signs no one in. |
| unset | set | Transition rule: the proxy secret below, exactly as before admin login. No login page; the header shows 프록시. A deprecation line is logged at start. |
| `builtin` | ignored | Name, password and TOTP code on the login form. |
| `oidc` | ignored | 로그인 button → OpenID Connect provider; the allowlist below decides. |

`proxy` is reserved for a later version; any other value stops the server at start.

Built-in admins live in the server database. Run the CLI inside the container, where `DB_PATH` already points at it:

```sh
docker compose exec switchboard switchboard admin create alice   # prompts for the password twice (or reads the first line of stdin); prints the otpauth:// URI and secret once
docker compose exec switchboard switchboard admin passwd alice
docker compose exec switchboard switchboard admin totp-reset alice  # new secret, printed once
docker compose exec switchboard switchboard admin disable alice
docker compose exec switchboard switchboard admin enable alice
docker compose exec switchboard switchboard admin list
```

A hosting PC instance (`switchboard up`, builtin mode) without any admin also opens a first-run setup page, `http://127.0.0.1:<port>/setup` ([Hosting instance on a PC](docs/hosting-pc.md), W4/L4); the plain server never does. It answers only loopback requests (loopback peer, listener and `Host`, no forwarding header), needs the one-time code in `<data>/setup-code` (printed once in the log; five wrong codes in a row replace it), and creates the admin only after one TOTP code from the QR code shown is confirmed. The first admin, from the page or `admin create`, removes the code file and turns `/setup` into `404`.

Passwords need at least 12 characters and are stored as argon2id hashes. `passwd`, `totp-reset` and `disable` end that admin's sessions; `enable` undoes `disable` and keeps the password and TOTP secret; `admin list` prints name, created, disabled and last login (the last accepted TOTP step; no secrets), `--json` an array of `{"name","created_at","disabled","last_login"}`; for the other actions `--json` prints `{"name","action"[,"secret","otpauth_uri"]}`. `POST /auth/login` (`{"name","password","code"}`) accepts the TOTP code (RFC 6238: SHA-1, 30 s, 6 digits) of the current step ±1, never the same step twice, and allows 5 failures per 15 minutes per name and per client IP; every failure, including the rate limit, is the same `401 login failed`. Success sets the `sb_session` cookie (`HttpOnly`, `SameSite=Strict`, `Secure` unless `SWITCHBOARD_INSECURE_COOKIE=1` for plain-http local use). Sessions (`admin_sessions`, only a SHA-256 of the cookie is stored) last 12 hours from the last request. `POST /auth/logout` ends the session; `GET /api/admin/me` returns `{"user","mode"}`. Login and logout need the same write guard as admin writes (below). Behind a reverse proxy every client has the proxy's address; set `SWITCHBOARD_TRUST_FORWARDED=1` when the proxy sets `X-Forwarded-For` (its last entry is then the client IP), and only then.

**OIDC mode**

| Variable | Value |
|---|---|
| `SWITCHBOARD_OIDC_ISSUER` | Issuer URL; discovery is `<issuer>/.well-known/openid-configuration`, fetched on the first login. |
| `SWITCHBOARD_OIDC_CLIENT_ID` | The client registered at the provider. |
| `SWITCHBOARD_OIDC_CLIENT_SECRET` | Optional. Set: a confidential client (the secret goes to the token endpoint). Unset (and no `_FILE`): a public client, PKCE only with token endpoint auth method `none`. |
| `SWITCHBOARD_OIDC_CLIENT_SECRET_FILE` | A file holding the client secret (surrounding white space trimmed), instead of `SWITCHBOARD_OIDC_CLIENT_SECRET`; setting both stops the server at start. |
| `SWITCHBOARD_OIDC_ADMINS` | Comma-separated; each entry is an email (`admin@example.com`) or `sub:<subject>`. |
| `SWITCHBOARD_OIDC_SCOPES` | Default `openid email profile`; must include `openid`. |
| `SWITCHBOARD_PUBLIC_URL` | The dashboard's public origin, e.g. `https://mail.example`. |

Register the client at the provider with redirect URI `<SWITCHBOARD_PUBLIC_URL>/auth/callback`, the authorization-code grant and PKCE `S256`; a public client with token endpoint auth method `none`. `GET /auth/login` redirects there with state, nonce and PKCE kept in a 10-minute signed cookie (`sb_oidc`, `SameSite=Lax`, key new on every start, so a restart only fails logins in progress). The callback checks the ID token's issuer, audience, expiry, nonce and signature (provider JWKS, with an algorithm the provider's discovery advertises, e.g. RS256 or EdDSA); an email entry matches only with `email_verified: true`. Success sets the same `sb_session` as the built-in mode; every refusal is `403 login failed` and the reason is logged without tokens or secrets. Removing an admin from the list ends their sessions at the next start. A missing variable stops the server at start with the missing names. For Google, the issuer is `https://accounts.google.com`; for Keycloak, `https://idp.example/realms/<realm>`.

The rest of this section is the transition rule: `/api/admin/*` returns `401` unless `SWITCHBOARD_ADMIN_PROXY_TOKEN` is configured and the request includes the matching `X-Switchboard-Admin` header. The browser does not know this value. Configure a separate random secret in the private deployment `.env` and in the service's private reverse-proxy configuration; do not reuse any role or Authelia credential. The proxy must authenticate the browser session with Authelia before forwarding and must overwrite (never pass through) any incoming `X-Switchboard-Admin` header with the configured secret. Keep the backend bound to loopback/private networking so clients cannot bypass the proxy boundary. Requests without the secret cannot use admin APIs. Admin writes (`PUT`, `POST`, `DELETE`) additionally need `Content-Type: application/json` and `X-Switchboard-Dashboard: 1`, and `Sec-Fetch-Site`, when the browser sends it, must be `same-origin`; otherwise they get `403`. This is CSRF protection: the proxy authenticates by cookie, and the custom header forces a CORS preflight that a cross-site page cannot pass. `GET` needs none of these.

The 진행 tab (`#progress`) is the first tab and opens when the address has no hash (other hashes such as `#mail`, `#metrics`, `#q=<id>` work as before). It reads `GET /api/admin/progress` with the pending questions and permission requests. The list starts with 대기 (count next to it): pending questions, pending permission requests, sessions in error or blocked, open boss directives older than `SWITCHBOARD_ALERT_PENDING`, directives answered but not completed whose sessions sit idle (멈춤), and 남긴 것 (#470: one row per open item of the left ledger, 「적지 않음」 for an older CLI's ending answer; its second line is 「지시 #N」, which opens the directive, and [이슈] (a URL), [새 지시] (a directive number) and [버림] (a reason), calling `POST /api/admin/left/{id}/issue|pass|drop`), in that order of kind and oldest first within a kind, each row with kind, item, role and age. Below it is one row per service (the part of a role before the first `/`), most recently active first, under the chips 전체 · 문제 있음 (오류 or 막힘) · 오래된 지시: a badge with the worst live session state (오류 > 막힘 > 바쁨 > 유휴, an idle session with running sub-agents counting as 바쁨, 「세션 없음」 when none), the session count, the open directives (red when one is older than the threshold; those are counted on the tab), 남긴 것 (open items recorded by the service's roles) and 「마지막 소식」 (subject and age of the last report to a boss, else the last activity). Selecting a row opens it in the detail panel at `#progress/<kind>:<id>`: a question opens its 답하기, a permission request its 허용 / 거절, a session its 세션 detail, a directive its mail thread with 닫기 (`POST /api/admin/messages/{id}/close`), a service the sub-tabs 세션 (state, 서브 에이전트 N개 작업 중, how long, shortened folder), 답 없는 지시 and 마지막 소식. Below 600px the 대기 and service rows are two-line cards. The 메일 tab has a task filter (`task=`, exact match) next to the thread filter; `GET /api/admin/messages` also takes `id=`. The 세션 and 메일 tabs are a list with a right detail panel (440px; the whole screen below 720px): selecting a row opens it at `#<tab>/<id>/<sub>` (`#sessions/team%2Fworker-1/status`, `#mail/42/thread`), which reload and back/forward restore and live updates keep; Esc closes it and returns focus to the row. 세션 lists role, state (with running sub-agents), context, last turn, machine and label, with state chips and a search box; its detail has 상태 (also folder, parent, last report), 메일 (that role's last 20 messages) and, for a hosted session, 터미널. 메일 lists #, subject, sender → recipient, state and time under the six filters; its detail has 본문 (text, never HTML, with 「스레드 보기」) and 스레드.

The 지표 tab (`#metrics`, after 세션) reads `GET /api/admin/metrics` for the last 7 or 30 days: first-reply counts, p50/p90/max and a bucket bar chart with a per-recipient table; pending mail per role (rows over the threshold highlighted); the multi-round count and top threads (clicking one opens the 메일 tab filtered to that thread); error/blocked time per role and the sessions in such a state now. Its tab number counts what is over an alert threshold now: flagged pending rows plus current error/blocked sessions past a non-zero limit (hidden when 0).

Live updates: the page holds one WebSocket, `GET /api/admin/live` (the same admin auth as `/api/admin/*`; the `Origin` must be the request's host or `SWITCHBOARD_PUBLIC_URL`, else 403). After every successful write (and after a recipient opens a message) the server sends `{"type":"change","seq":N,"kinds":[…]}`, where kinds are tab names (`progress`, `sessions`, `metrics`, `mail`, `permissions`, `questions`, `settings`); the background sweep sends what its notices changed. The shown tab reloads its data (not while one of its fields has focus), other tabs reload when next shown and their counts update at once. On connect the server sends `{"type":"hello","boot":B,"seq":N,"reset":bool,"kinds":[…]}`; a reconnect passes `?boot=B&after=N` and gets the kinds it missed from a ring of the last 512 changes, or `reset:true` after a restart or a longer gap (everything reloads). Reconnects back off from 1 s to 30 s. A client that falls 64 changes behind is closed and reconnects with its cursor, so slow clients never hold up writes; at most 1000 connections, then 503. The socket re-checks the admin session every 30 s and closes when it ends. A reverse proxy must pass the WebSocket upgrade on `/api/admin/live`:

```nginx
proxy_http_version 1.1;
proxy_set_header Upgrade $http_upgrade;
proxy_set_header Connection "upgrade";
proxy_read_timeout 120s;
```

For nginx, keep your existing Authelia protection on the dashboard host and add this directive inside only this service's already-protected `location /` (substitute the private secret from your secret-management process; do not commit it):

```nginx
proxy_set_header X-Switchboard-Admin "<same random value as SWITCHBOARD_ADMIN_PROXY_TOKEN>";
```

This replaces any browser-supplied admin header, while leaving ordinary role-token API requests intact for CLI use. The dashboard itself does not send an `Authorization` header. Validate nginx configuration before reloading it. If Authelia protects only selected paths, also protect `/api/admin/` with the same authenticated session check.

Backup and restore while stopped (SQLite WAL is checkpointed on clean shutdown):

```sh
docker compose stop
mkdir -p backup
docker run --rm -v switchboard_switchboard_data:/data -v "$PWD/backup:/backup" alpine sh -c 'cp /data/mail.db /backup/mail.db'
docker compose start

# Restore: stop service, copy a verified backup back to /data/mail.db, then start.
```

Use the actual volume name from `docker volume ls` if Compose prefixes it differently. Retain and protect the token file separately from database backups. For safe online backups use SQLite's backup API or briefly stop the container as above. Moving to another host: [docs/move-host.md](docs/move-host.md).

## API

All `/api/*` routes except registration require `Authorization: Bearer <role-token>` and `X-Switchboard-Role: <expected-role>`. The server checks that the selected role matches the credential, so a session cannot accidentally use another profile's identity. Unauthorized or mismatched requests return 401; a recipient outside the registered role set returns 403. `POST /api/register` accepts `{role,credential}` and requires the operator enrollment bearer credential for new roles. Existing roles may only be resumed by presenting their same role credential.

- **Stored tokens.** The `roles` table keeps `sha256:<hex sha256 of the token>`, never the token; seeding from `SWITCHBOARD_TOKENS`, registration and resume all store or compare that hash in constant time. On start the server hashes every row without the prefix in one transaction, after copying those rows to `roles_plain_backup`, and logs `role tokens: hashed N plain rows; plain copies kept in roles_plain_backup` (nothing when there is none). Clients keep their tokens. Neither tokens nor hashes appear in any response or log. `roles_plain_backup` holds plain tokens, so the next start drops it: it first copies the whole database next to its file as `<db file>.pre-drop-plain-backup-<UTC YYYYMMDDTHHMMSSZ>` (mode 0600, never overwriting an existing file), then drops the table and logs `role tokens: dropped roles_plain_backup (N rows); copy before drop at <path>`. When the copy fails it logs `role tokens: kept roles_plain_backup; copy before drop failed: <error>`, keeps the table and tries again on the next start. The drop runs before the hashing step, so a backup written on the same start (after a rollback) is kept until the start after. That copy is the only way back to a binary from before hashing.
- **Revoke.** `POST /api/admin/roles/{role}/revoke` and `POST /api/admin/roles/{role}/restore` (admin proxy and write guard; role slashes stay path separators) return `{role, created_at, revoked_at, group, last_used_at, last_machine}`. A role whose slot reported (register or heartbeat) within the last 24 hours is not revoked without `?force=1`: the revoke answers 409 `{error, last_used_at, machine}`; the dashboard confirm names the last use and the CLI `roles revoke` prints it and exits 2 without `--yes`. A revoked role gets 401 with body `role revoked at <RFC 3339 time>` (a wrong token keeps `unauthorized`) on every role endpoint under every name it covers (`<role>-N` included), registration resume included; its live slots are released at once (offline, no offline notice) and an open `/api/events` stream ends at its next keep-alive. Each sender with pending mail to the role (or its `<role>-N` mailboxes) gets one system mail `recipient revoked: <role>` listing that mail (id, subject, sent time); the mail itself is kept as it is, stays readable in the dashboard, and is left out of the pending metric, the pending alert, 진행 대기 and the [미수신] notice until restore. Restore clears `revoked_at`; the same token works again. `GET /api/admin/roles` returns `[{role, created_at, revoked_at, rotated_at, retired_at, group, last_used_at, last_machine}]` (`last_used_at` is empty when no slot reported; `revoked_at`, `rotated_at` and `retired_at` null unless revoked, rotated or retired; `group` is the role's group prefix, empty for an internal role).
- **Rotate and retire (#7).** `POST /api/admin/roles/{role}/rotate` with `{"credential": NEW}` (24 characters or more, not the enrollment credential, not the current one; 400 otherwise) replaces the role's own token: the old one gets 401 at once under every name of the role, the new one resumes registration, and the role's slots, mail and hosted role credentials stay. A revoked role may be rotated (the new token works after restore). The answer is the role row with `rotated_at`, never the token. `POST /api/admin/roles/{role}/retire` revokes the role as above (same `?force=1` rule for a role in use) and marks it retired: restore and rotate answer 409 `role retired`, registration under its name stays refused, retiring again keeps the first `retired_at`. Its row and its mail stay, so the dashboard still lists the role and reads its mail. A boss role reaches both at `/api/boss/roles/{role}/rotate` and `/retire` inside its view; the boss write record holds the path, never the credential. The CLI `roles rotate ROLE --token-file PATH --yes` sends the token in PATH, or, when PATH is missing or empty, writes a new random one there owner-only first and sends that; it never prints the token. `roles retire ROLE --yes` names the role's last use like `roles revoke`.
- **Rename.** `POST /api/admin/roles/{old}/rename` with `{"to": NEW}` (admin proxy and write guard) moves a role to a new name in one transaction and returns `{role, aliases}`. The role keeps its token; stored mail, mail states, slots, presence log, questions, permissions, question settings, group boss and invite references to `<old>` and `<old>-N` (and `label:<old>/…` addresses) are rewritten to the new name; `<old>` is kept in `role_aliases`. From then on `<old>` and `<old>-N` authenticate with the same token as the new role (requests act as the new role), mail sent to them or to `label:<old>/…` is delivered to the new role, and registering `<old>` again is refused (409). Renaming an already renamed role re-points its aliases, so aliases never chain. 404 when `<old>` is not a role; 409 when the new name (or its base) is a role or an alias, or when a separate role `<old>-N` / `<new>-N` exists. Not covered: `SWITCHBOARD_BOSS_ROLES` and group membership follow the name, so update the environment and group prefixes yourself; event streams opened under the old name before the rename wake again after they reconnect.
- **Collaborator groups.** A group is a role prefix: a role belongs to the group whose `<prefix>/` starts its name (longest prefix wins); a role in no group is internal. `GET /api/admin/groups` lists `[{prefix, boss_role, created_at, revoked_at}]`; `GET|PUT|DELETE /api/admin/groups/{prefix}` (admin proxy; writes also the write guard). PUT takes `{boss_role?}` (default `<prefix>/boss`) and creates the group or updates it (restoring a revoked group, not its roles). DELETE revokes the group and every role in it and cancels its open invites; registration under a revoked group returns 403. With no groups every role is internal and nothing below applies. The dashboard has no groups or invites view; these admin endpoints and the CLI are the only way to manage them.

  | | Internal role, global boss | Group role |
  |---|---|---|
  | Send (`POST /api/messages`, reply) | anyone | global bosses (`SWITCHBOARD_BOSS_ROLES`), its group's `boss_role`, roles of its group, and the sender of mail it is replying to; else 403 `outside your group` |
  | Presence (`GET /api/presence`) | every session | its group's sessions |
  | Events, poll, watch, mail | own mailbox | own mailbox |
  | Questions, decisions, permissions | own base; a global boss also those of internal askers | own base; the group's `boss_role` also those of its group |
  | Who answers (questions, permissions; with nobody, permissions get 409 and questions go to the dashboard) | global bosses | the group's `boss_role` only; a global boss gets the group's questions only as a watcher in question settings |
  | Metrics, progress, alerts | global bosses | 403 (a group boss too) |
  | Boss writes (`POST`/`PUT`/`DELETE /api/boss/<admin path>`, #399) | global bosses: the dashboard admin's writes | the group's `boss_role`: targets of its group only; 403 on the limit, nodes and the `*` question setting; other roles 403 |
  | Boss views (`GET /api/boss/…`: mail, jobs, roles, settings, terminals) | global bosses: every role; the server summary and secret setting names in settings | the group's `boss_role`: mail with a sender or recipient in its group, and its group's jobs, roles, question settings, refusals, records, their nodes and scheduled runs; no server summary; other roles 403 |
  | Reports (`POST`, `GET /api/reports`) | global bosses | the group's `boss_role`; linked mail must have a sender or recipient in its group |
  | Search (`GET /api/search`, #481) | everything | its group's mail (sender or recipient), questions (asker), reports (author) and left items (either side of the directive); the group's `boss_role` also the groups it answers for. Others are neither listed nor counted |
- **Invites and join.** A global boss role (`POST /api/invites`, else 403) or a signed-in admin (`POST /api/admin/invites`, write guard) creates a one-time code with `{prefix, role?, ttl?}`: `ttl` is a Go duration or whole days (`7d`), default `72h`, at most `30d`; `role`, when given, pins the invite to that role under `<prefix>/`. The answer (201) is `{id, prefix, role, expires_at, created_by, created_at, code, group_created}`; the code (128 random bits, base32 with dashes) appears only there and is stored as a hash. When the prefix has no group, the group is created with `boss_role` `<prefix>/boss`; if roles already exist under `<prefix>/` this is refused with 409 (they would become group roles and lose access), and a revoked group also gets 409. `GET /api/admin/invites` lists open invites; `DELETE /api/admin/invites/{id}` cancels one (404 when not open). `POST /api/join {code, role?, credential}` needs nothing but the code: the role defaults to the invite's role and must equal it when set, otherwise it must be under the invite's prefix (403); the credential needs 24+ characters and is stored hashed; 409 when the role exists. A code works once: unknown, used, cancelled and expired codes all get the same 410, and those count per client IP like failed logins (429 after 5 in 15 minutes). The answer is `{role, group, boss_role, status: "joined"}`. `GET /api/admin/collaborators` answers each group with `roles` (`role, created_at, revoked_at, online, last_seen`) and open `invites`; the dashboard 협업자 tab shows it, creates invites (the code shown once), cancels invites and revokes roles and groups, each after a confirm.

  CLI: `switchboard invite --prefix partner-a [--role partner-a/dev] [--ttl 72h] [--json]` (a global boss profile) prints the code and a join line. The collaborator runs `switchboard join https://mail.example CODE [--role partner-a/dev] [--profile NAME]` once: it makes the token locally (crypto/rand), joins, and writes a new profile (`<config>/switchboard/<NAME>.json`, mode 0600, the same format as `config set`; default name from the server host, e.g. `mail-example`; an existing profile is never overwritten). It prints the role, group, profile path and the plugin env line (`SWITCHBOARD_PROFILE=NAME`, plus `SWITCHBOARD_CONFIG_DIR` when set), never the token.
- **Who am I.** `GET /api/whoami` (any role) answers `{role, base, group, global_boss, boss_of, is_boss}`: `group` is the caller's group prefix (`""` when internal), `global_boss` whether it is in `SWITCHBOARD_BOSS_ROLES`, `boss_of` the live groups whose `boss_role` is the caller, and `is_boss` is `global_boss || boss_of` non-empty. A client shows a boss panel when `is_boss` is true; the panel's `GET /api/questions/poll` and `GET /api/permissions` then return exactly what that boss answers.

- `POST /api/messages` with `{recipient,subject,body,task_id?,thread_id?,reply_to?,priority?}`. `priority` is `normal` (default when omitted) or `urgent`; any other value returns 400. Optional `Idempotency-Key` header; a retry returns the first message, including its priority.
- Send to a revoked role (directly, as `<role>-N`, as `label:<role>/…` or by an old name) returns 410 `recipient role revoked at <time>` and stores nothing; a retry with the same `Idempotency-Key` gets the same answer. The CLI prints it and exits non-zero.
- Every message in a JSON response (send, reply, list, read, admin list) includes `"priority":"normal"|"urgent"`. Messages stored before priority existed are `normal`.
- `GET /api/messages?box=inbox|outbox&q=...&status=...`
- `GET /api/messages/{id}`; recipient read marks `read`, sender may inspect own outbox messages.
- `GET /api/search?q=PATTERN` (#481; `GET /api/admin/search` for the dashboard) finds text in mail (subject, body), reports (title, body), panel questions (question, options, chosen answer) and left items. `q` is a substring, or a Go regexp (RE2) with `regex=1`; both ignore case unless `case=1`. Narrow with `kind=mail|report|question|left` (repeatable), `role=R` (a sender or recipient, an author, an asker; a slot or label counts for its base), `thread=N`, `since`/`until` (RFC 3339 or `YYYY-MM-DD`, UTC; `until` takes the whole day) and `limit` (default 50, at most 200). The answer is `{hits:[{kind,id,at,from,to,title,line,thread,directive,open}],next,cut,scope}`, newest first: `line` is the matched line cut to about 160 characters around the match, `open` the command that opens the record (`read N`, `report show RN`, `question show ID`; a left item opens its directive), `next` the cursor for `after=` when there is more, `cut` true when the 2-second limit stopped the search (the hits are what it found). The rows are scanned, not indexed: 6,000 made-up messages of about 2 KB take 30–70 ms when nothing matches, and an FTS5 trigram index cannot find words shorter than three characters (most Korean words) nor run a regexp (`internal/search/bench_test.go`). The pattern is not logged. 400 on an empty pattern, a bad regexp or a bad parameter.
- `POST /api/messages/{id}/reply` with `{subject?,body,recipient?,priority?,directive?,done?}` (`subject` defaults to `Re: ` and the replied-to subject) (same `priority` rules as send, same `Idempotency-Key` header). `directive: true` marks a reply that carries new work (see progress); messages include `"directive":true` only when set. `done: true` stores the reply and marks the replied-to message `complete` for its recipient in the same transaction; a retry with the same key returns the first reply and marks nothing twice. A reply to a directive answers with `"directive_state":"open"|"done"`, the directive's state after the reply (see Directives).
- `POST /api/messages/{id}/ack`, `/complete`; recipient only.
- What is left (#470): `reply`, `send` (with `complete`), `/complete` and `/close` take `left` (strings) or `left_none: true` (in the message body; for `/complete` and `/close` an optional `{left?,left_none?}` body). With `X-Switchboard-Left` set, an answer that ends a directive (see Directives) with neither is refused 400; `left` on an answer that ends none is 400. `POST /api/left` with `{directive,left:[…]}` adds to a directive the caller (its recipient or sender) ended (409 while open). `POST /api/left/{id}/issue` with `{url}` and `/pass` with `{directive}`: the directive's sender base only (403), 409 once the item is not open. `POST /api/admin/left/{id}/drop` with `{reason}` (also `/issue`, `/pass` for the dashboard): a signed-in admin only; a boss token is refused.
- `POST /api/messages/{id}/close`; sender only (anyone else 403, no such message 404). The sender marks its directive as needing no answer: it stores `no_reply` (as `--no-reply` does), so the directive leaves `progress` and gets no more reminders. Mail that is not a directive (a plain reply, system mail) returns 400, except an answer the caller received to a directive it sent: that closes the directive and marks the answer complete for the caller in one transaction, answering `{"id":DIRECTIVE,"closed":true,"completed":ANSWER}`. Idempotent; answers `{"id":N,"closed":true}`, with `"withdrawn":true` when the recipient had not read or answered the directive: it is then withdrawn as well (#354, next item). CLI: `switchboard close ID [--json]` prints `#ID closed; withdrawn (the recipient had not read it)` or `#ID closed; the recipient already read it, so it stays in its mailbox marked as needing no answer`, or `#N closed; #ID complete` for an answer (`--json` the answer).
- `POST /api/messages/{id}/withdraw` (#354); sender only (anyone else 403, no such message 404). Takes back mail the recipient has not read, acknowledged, completed or replied to: 409 otherwise (close it or send new mail). The row is kept with status `withdrawn`, `withdrawn_at` (column added in place by `store.Init`), `no_reply` set and `addressed_to` the mailbox it was going to; it leaves the recipient's inbox, read, watch, events and polls, the pending metric and alert, the [미수신] notices and held or handed-off delivery, and the sender's outbox shows it as `withdrawn`. Idempotent; answers `{"id":N,"withdrawn":true}`. CLI: `switchboard withdraw ID [--json]` prints `#ID withdrawn`. `POST /api/admin/messages/{id}/close` does the same for an admin (dashboard write guard as for other admin writes), for any sender.
- `GET /api/watch?after=<message-id>` waits up to 25 seconds, returns `{messages:[ids],cursor:id,timeout?:true,answers_directive?:{"<message id>":{"id":N,"state":"open"|"done"}}}` (`answers_directive` only for messages that answer a directive the role sent; see Directives). Replay with the returned cursor. IDs are durable; concurrent watchers independently replay and can see duplicates.
- `GET /api/events` streams new pending mail for the authenticated role as server-sent events (same two auth headers; `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `X-Accel-Buffering: no`). Optional cursor: `Last-Event-ID: <message-id>` header, or `?after=<message-id>` (the header wins); a non-integer cursor returns 400. On connect the server sends `retry: 3000`, then a backlog of `event: message` frames, then `event: ready` with `{"cursor":<last id sent or the given cursor>}`, then live `event: message` frames as mail is stored, and `: ping` comments every `SWITCHBOARD_SSE_KEEPALIVE` (Go duration, default `20s`). Each message frame carries `id: <message-id>` and `data: {"id","sender","recipient","subject","priority","created_at","task_id"?,"thread_id"?,"body"?,"answers_directive"?}`; `priority` is `normal` or `urgent` and `body` is present only for urgent mail. `answers_directive` is `{"id":N,"state":"open"|"done"}` when the mail is a reply in the thread of directive N that the recipient (the streaming role) sent, with N's state under `mail.AnsweredRule.Open` when the event is built (see Directives); a session plugin can say "answers directive #N, still open" from `data.answers_directive.id` and `data.answers_directive.state == "open"`. Old clients ignore it. Without a cursor the backlog is every message whose recipient state is still `pending`; with a cursor it is pending messages with a larger ID. Within one connection each message is sent at most once, in ID order; reconnecting with the last received `id` never repeats a message at or below it, while reconnecting without a cursor resends whatever is still pending, so clients dedupe by ID. Streaming has no state side effects. Example: `curl -N -H "Authorization: Bearer $TOKEN" -H "X-Switchboard-Role: worker" -H "Last-Event-ID: 41" https://mail.example/api/events`.
- `GET /api/events/poll?after=<message-id>&timeout=<seconds>` is the long-poll form of `/api/events` for clients that can only read a complete response (same two auth headers, 401 otherwise). It uses the same cursor rules (`Last-Event-ID` header or `?after=`, header wins; no cursor means every message still `pending`) and returns the same event objects as the stream's `data` (including `answers_directive`, at `events[i].answers_directive`), as `{"events":[...],"cursor":N}` with `Content-Type: application/json` and `Cache-Control: no-store`. `cursor` is the ID of the last event returned, or the request cursor (0 without one) when `events` is empty; pass it back as `after`. When pending mail after the cursor exists it answers at once (at most 200 events per response, oldest first; poll again for more); otherwise it waits for new mail for the role and answers as soon as some is stored, or with an empty list when `timeout` passes. `timeout` defaults to 25 seconds, `0` answers at once, and values above `SWITCHBOARD_POLL_MAX` (whole seconds, default `55`, below a typical 60-second proxy read timeout) are capped. A non-integer or negative `after`/`timeout` returns 400. Polling has no state side effects; server shutdown answers waiting polls with an empty list. Example: `curl -H "Authorization: Bearer $TOKEN" -H "X-Switchboard-Role: worker" "https://mail.example/api/events/poll?after=41&timeout=25"`.
- **Numbered slots.** A base role (say `team/worker`) can be held by several sessions as `team/worker-1`, `team/worker-2`, … The base role's token authorises every `team/worker-N` (N = 1…999, no leading zeros) in `X-Switchboard-Role`; a token of another base gets 401. A role row registered under the exact name (for example a separately enrolled `team/lead-2`) always wins: only its own token works for that name and slot registration skips that number. The number need not be currently leased to authenticate, so mail queued for an expired slot stays readable.
- **`team/worker` and `team/worker-1` are one mailbox.** Mail to the unnumbered base goes to slot 1. It is stored under the base name, so clients that never register (header `team/worker`) and the session holding `-1` see the same inbox, read/ack/complete state, `wait`, `/api/events` and `/api/events/poll` wake-ups; mail sent by `-1` carries sender `team/worker` and `recipient` of mail to `-1` reads `team/worker`. `-2` and above see only their own mail. Mail may be sent to any `-N` of a registered base whether or not it is leased; it waits there.
- `POST /api/slots/register` with `{machine,directory,session_id?,label?,parent?}` (fields up to 512 bytes; `machine` and `directory` required, else 400) assigns a numbered slot under the caller's base, atomically in one SQLite transaction. The same machine+directory gets its previous number back, even before its lease ends; a new identity gets the smallest free number. Response: `{"role","base","number","machine","directory","session_id"?,"label"?,"parent"?,"registered_at","lease_expires_at","lease_seconds","other_active","reclaimed"}`; `other_active` counts the base's other leased slots (for a duplicate warning).
- `POST /api/slots/heartbeat` (same body) extends the identity's lease and updates `session_id`/`label`/`parent`; it answers with the same shape. If a takeover moved the slot, the answer's `role` is the new one. 404 means the identity holds no slot any more (its number was reassigned after expiry): register again. `POST /api/slots/release` (same body) ends the lease now.
- `POST /api/slots/takeover` (same body) gives the caller number 1. A leased previous holder moves to the smallest free number other than 1, keeping its lease, and is reported as `displaced`; an expired holder is dropped. The caller's own previous number is released. 409 when `<base>-1` is a separately registered role.
- Leases last `SWITCHBOARD_PRESENCE_INTERVAL` × `SWITCHBOARD_PRESENCE_MISSED` (default `60s` × `3` = 3 minutes); `SWITCHBOARD_SLOT_LEASE` (Go duration), when set, overrides that product. An expired slot leaves the slot table and its number becomes free; its mail stays queued. Expiry is evaluated lazily when slots are read or assigned. `GET /api/slots` lists the leased slots of the caller's base; `GET /api/admin/slots` (admin proxy only, read-only) lists every base. CLI: `switchboard slots [--json]` and `switchboard slot register|heartbeat|takeover|release [--machine NAME] [--directory PATH] [--session-id ID] [--label TEXT] [--parent ROLE] [--json]` (machine and directory default to this host and the current directory).
- **Session presence.** Register, heartbeat and takeover also carry the session's presence: `state` (`idle`, `busy`, `compacting`, `error:<kind>` when the turn failed, e.g. `error:StopFailure`, or `blocked:<kind>` when the session waits on a person, e.g. `blocked:permission_prompt`; `<kind>` is 1–64 characters from `A-Z a-z 0-9 . _ -` and the prefix is lowercase and exact; anything else is 400, and the state is stored and returned verbatim), `context_tokens` (whole number ≥ 0, else 400), `last_turn_at` (RFC 3339, else 400) and `subagents` (the number of background sub-agents the session started that have not ended; a whole number ≥ 0, else 400, stored at most 64), all optional. Other unknown fields are ignored. Sessions send a heartbeat when their state changes and every `SWITCHBOARD_PRESENCE_INTERVAL` (Go duration, default `60s`). A heartbeat keeps fields it leaves out, except `subagents`, which every register, heartbeat and takeover sets (absent means 0); register and takeover start from what they send. One rule decides offline: **a session is offline exactly when its slot lease has ended**, i.e. after `SWITCHBOARD_PRESENCE_MISSED` (default `3`) missed heartbeats, or at once after `release`. The number is then free for others; the same identity reporting again before anyone takes it is online again on the same number (otherwise heartbeat gets 404 and it registers again).
- **CLI versions.** Every CLI request sends its build version in `X-Switchboard-Version`; register and heartbeat record it on the slot (`cli_version` in the presence JSON: a tag, `dev`, or `unknown` for a slot claimed without the header; a heartbeat without it keeps the recorded version; empty until the slot reports again). The server's minimum is `SWITCHBOARD_CLI_MIN` (`v0.26`, `0.26` or `v0.26.0`; default the server's own major.minor, read from a tag or `git describe` build; an invalid value logs one line and keeps the default; a `dev` server has none). Versions compare by major.minor; `cli` is `current`, `old` (옛 판) or `unknown` (no header or not a release tag, never old). The dashboard's 세션 list has a 판 column with an 옛 판 badge, and 진행 → 대기 has one 옛 판 row per machine (`cli_behind` in the progress JSON: machines whose online sessions run an old CLI; `unknown` is shown as 판 모름 but not listed; none on a server without a minimum). Once per UTC day and machine the sweep mails every boss role from the system sender: subject `[옛 판] <machine> switchboard vX (서버 vY)` (vX the lowest on that machine), body the machine, each role with its version, and a last line with the server and minimum versions saying the version is the one the session read at start and clears when the session is restarted after the CLI on disk is upgraded; nothing when every machine is current. `GET /health` answers `{ok, version, cli_min}`.

- **Label addresses.** Mail may be addressed to `label:<base>/<label>` (for example `label:team/worker/issue-17`) before any session carries that label. `<base>` must be a registered role (else 403); `<label>` is 1–128 characters from `A-Z a-z 0-9 . _ -` (the label is the part after the last `/`); any other `label:` form is 400. If a leased slot of `<base>` has that label (the `label` field of register/heartbeat/takeover), the message goes straight to that slot's mailbox (the smallest number when several do). Otherwise it is **held**: stored with `recipient` `label:<base>/<label>` and `status` `held`, shown in the sender's outbox and the admin list (`box=held`), and in no inbox. The first session of `<base>` that registers, heartbeats or takes over with that label receives every held message for it, atomically in the same transaction (the grant's `held_delivered` counts them), and its event stream or poll wakes. Held mail does not expire. Labels are scoped to the base on purpose: any token can register any label for its own base, so an unscoped label such as an issue number could be collected by a session of another team; sessions of other bases never receive the mail. A moved message gets a **new ID** (so event and watch cursors that already passed the old ID still see it); `held_id` is the ID returned at send time, which still resolves to the message (#392, see above). Message JSON (and outbox) shows the final `recipient`, plus `addressed_to` (the label address) for label mail, and `held_at`/`delivered_at`/`held_id` when it was held; event data carries `addressed_to`. CLI: `switchboard send --to label:team/worker/issue-17 ...`.
- **Stall notices.** The server sweeps every `SWITCHBOARD_SWEEP_INTERVAL` (default `30s`) and sends ordinary (`normal`) mail from the system sender `switchboard/system`. (1) When a session's lease ends without a release, its presence `parent` gets one notice (subject `offline: team/worker-2`, body like `Session team/worker-2 (label issue-17, machine box-1, directory /work/repo) went offline at 2026-01-01T10:03:00Z; last report 2026-01-01T10:00:00Z.`). No repeats while it stays offline; a session that comes back and goes offline again is noticed again. A release (`POST /api/slots/release`) is an intended stop and sends nothing. No notice is sent when the parent is empty, not a registered role, or the session itself. (2) When mail to `label:<base>/<label>` stays held for `SWITCHBOARD_LABEL_STALL` (default `10m`), its sender gets one notice per label (subject `label not connected: label:team/worker/issue-17`) listing the held message IDs; the mail stays held and is still delivered when the label connects. (3) Directive reminders, off unless `SWITCHBOARD_REMIND=on`: an open directive (as in `progress`, below) that its recipient has read (status `read`), to a role that is not a boss, gets a reminder to that recipient (subject `[다시 알림] #<id> <subject>`, body `#<id> 가 끝났으면 reply --done 으로 보고하고, 아직이면 reply 로 진행을 알려라`, idempotency key `remind:<id>:<n>`) once it has had no reply for `SWITCHBOARD_REMIND_AFTER` (default `2h`; counted from the directive, or its newest reply), each next one twice the previous gap later (2h, 6h, 14h), at most `SWITCHBOARD_REMIND_MAX` (default `3`); when it is still open one more gap after the last one, its sender gets one notice (subject `[안 끝남] #<id> <subject>`, key `remind-sender:<id>`). `reply --done`, `complete` or the sender's `close` stops them; a plain reply only pushes the next one a gap later, and reading does nothing. The first sweep with it on records the time in `remind_state`, and switching it off and on keeps the first time. A directive older than that time counts from it (#268): its first reminder is due at that time + `SWITCHBOARD_REMIND_AFTER`, so switching on sends nothing at once and older directives are reminded one gap later. Off, the sweep sends and writes nothing. (4) Idle open directives (#268, #269): for each recipient mailbox, its newest open directive from a boss role (replied to or not), when the recipient is not a boss, counts as stalled once the live session reading that mailbox (slot 1 for `<base>`, slot N for `<base>-N`) has been `idle`, with no sub-agent running, for `SWITCHBOARD_REMIND_IDLE` (Go duration, default `1h`, `0` off) since the latest of the directive, its newest reply and the start of the idle stretch. It shows in 진행 → 대기 as a 멈춤 row (`progress` JSON: `stalled` per service, `idle_after_s` at the top) whether reminders are on or off; with reminders on, its sender gets up to `SWITCHBOARD_REMIND_IDLE_MAX` notices (default `1`, one threshold apart; subject `[멈춤] #<id> <subject>`, keys `idle-after:<id>`, then `idle-after:<id>:<n>`), never earlier than `SWITCHBOARD_REMIND_IDLE` after the reminders were switched on. A session busy again, `reply --done`, `complete`, `close` or a newer open directive to the mailbox ends the row. No live session is not idle: the offline notice (1) covers it. Notices never contain tokens. At start-up the server logs one line next to `admin auth: …`: `directive reminders: on (after 2h, max 3, since <RFC 3339 time or first sweep>, idle 1h, idle max 1)` or `directive reminders: off (idle 1h, idle max 1)`, `idle off` in place of `idle 1h, idle max 1` when `SWITCHBOARD_REMIND_IDLE=0`; the dashboard's 설정 → 다시 알림 shows the same values (`idle`, `idle_seconds`, `idle_max` in the settings JSON).
- **Progress.** `GET /api/progress` (boss roles in `SWITCHBOARD_BOSS_ROLES` only, everyone else 403) and `GET /api/admin/progress` (admin proxy only) answer, per service (the part of a role before the first `/`), what it is doing now and when it was last heard from: `{"generated_at","pending_alert_s","services":[{"service","badge","sessions":[{"role","state","since","directory","last_seen","subagents"?}],"last_report":{"id","from","to","subject","at"}|null,"last_activity_at"|null,"open_directives":[{"id","to","subject","status","age_s","over_threshold","replied_at"?,"recipient_state"}],"stalled":[…],"left"}],"left":[{"id","directive","kind","text"?,"recorded_by","recorded_at","state","directive_from","directive_subject"}]}`, services sorted by `last_activity_at` (newest first, none last). `sessions` are the online sessions (`state` idle, busy, compacting, `error:*`, `blocked:*`, or `unknown` when none was reported; `since` is when the current state began, `last_seen` the last report, `subagents` the running background sub-agents, omitted when 0); `badge` is the worst of them (`error` > `blocked` > `busy` (compacting, and an idle or unknown session with `subagents` > 0, count) > `idle`, `none` without sessions). `last_report` is the newest mail from the service to a boss role; `last_activity_at` the newest mail sent by any role of the service (`switchboard/system` mail never counts). `open_directives` is mail from a boss role to the service — a send, or a reply sent with `directive` (`reply --directive`); a plain reply is not a directive — not sent with `--no-reply` nor closed by its sender (`close`), and whose recipient status is not complete, oldest first: the open directives (see Directives; replies leave a directive open, `reply --done` or `complete` by the recipient closes it, `read` does not). `replied_at` is its newest reply (a later message by a role of the recipient's base, not `switchboard/system`, to the sender's base, with `reply_to` the directive or in the directive's thread; `over_threshold` when older than `SWITCHBOARD_ALERT_PENDING` (`pending_alert_s`, 0 = off). The dashboard calls them 열린 지시 and shows the recipient as 오프라인 or 유휴 apart. CLI: `switchboard progress [SERVICE] [--json]` (boss roles) calls `GET /api/progress` and prints one block per service, or only SERVICE: `<service> [<badge>] 마지막 소식 <N분 전|N시간 전|N일 전> — <subject>` (or 보고 없음 / 소식 없음), then the live sessions (`role state folder`, followed by ` · 서브 에이전트 N개 작업 중` while sub-agents run, the folder cut to its last two elements as `…/workspace/switchboard`), and the open directives with their age (`!` marks one over the threshold), and `남긴 것 N` when its roles left open items; after the blocks, `남긴 것 N` and a line per open item (`#ID 지시 #D role age — text`, `(적지 않음)` for an older CLI's). Relative times count from `generated_at`. `--json` prints the whole API JSON unchanged; a 403 or an unknown SERVICE is an error.
- **Reports.** A boss role (a global boss or a group's `boss_role`, else 403) ends its work with a report: `POST /api/reports` with `{"title","request"?,"body","mail"?:[id…],"idempotency_key"?}` (or the `Idempotency-Key` header; a retry with the same key returns the first report with 200, a new one is 201). `title` and `request` (what was asked) are one line; `body` is Markdown. `mail` links the directive threads the work went through: each ID resolves to its thread's root, so a reply links its directive; an ID that does not exist or that the caller's group cannot see fails the whole call with 400 naming it. Linked mail the caller received (it is the recipient) is marked complete for it in the report's transaction; other linked mail is only linked. `#N` in the body is never a link. The answer is `{"id","author","title","request","body","created_at","mail":[root id…],"status","last_reply_at","directives","open_directives"}`. `status` is derived, never stored: a report is `open` (진행 중) while at least one linked directive is open under `mail.AnsweredRule.Open` (see Directives: not done by its recipient and not closed, whatever replies it got), and `done` (완료) otherwise or when it has no links. `directives` counts the linked threads whose directive still exists and `open_directives` the open ones, so `status` is `open` exactly when `open_directives > 0`. `GET /api/admin/reports` lists them newest first without bodies; `GET /api/admin/reports/{id}` adds `"threads":[{"directive","replies":[…],"answered","completed","closed","open"}]`, each message `{"id","sender","recipient","subject","body","created_at","status","answers"?}` (`answers`: the mail is a reply to the directive; `answered`: the directive got one). A report, and every mail write, publishes the `reports` change on the live bus. CLI: `switchboard report --title TEXT [--request TEXT] [--mail ID[,ID...]]... (--body TEXT | --body-file PATH | stdin) [--idem KEY] [--json]` prints the new report ID, or the stored report with `--json`. A boss role reads reports too: `GET /api/reports[?status=open|done]` is `GET /api/admin/reports` and `GET /api/reports/{id}` is the admin detail (each message also carries `recipient_live`, false when the recipient's role is revoked), limited to the reports whose author the caller may see (a group's boss: its own group's; a report outside it is 404). `switchboard report list [--open] [--json]` prints one line per report, `<id> <status> 열린 지시 <open>/<all> <created> <title>`, and with `--open` only the open reports, each followed by its open directive threads, `  #<id> <sender> → <recipient> <sent> <recipient's status> <살아 있음|폐기됨> <subject>`; `switchboard report show <id>` (the number the dashboard shows in #reports/<id>; an R prefix is accepted) prints one report with all its threads. The report's open is the answered rule's Open over the linked roots, which is not the progress view's open directive: progress counts only boss-sent mail to a live recipient, so a root to a revoked role or one sent by a non-boss shows open here and not there. Dashboard: 보고 (운영 group) lists title, author, status (진행 중 with its count, `진행 중 · 열린 지시 1/2`, or 완료) and time with a 전체 / 진행 중 / 완료 filter, the menu count being the 진행 중 reports; the detail shows the request line, the body rendered as Markdown (headings, lists, tables, fenced and inline code, `**strong**`, http(s) links only; built from text nodes, so markup in a body stays text), then each linked thread, the directive marked 열림 or 끝남 (an open one also shows `닫을 쪽 <sender>`, the role that closes it) and its replies, each opening the mail detail.
- **Rules ledger.** The decisions (결정) and tips (요령) in force, by service and topic (`internal/rules`). A row is `{"id","kind":"decision"|"tip","text","topic","group","scope":{"kind":"all"|"service"|"tag","values"?},"sources"?,"source_text"?,"status":"active"|"replaced"|"void"|"proposed"|"rejected","replaces"?,"replaced_by"?,"device"?,"match"?,"author","created_at","voided_by"?,"voided_at"?,"reviewed_by"?,"reviewed_at"?,"review_note"?}`. `scope` is every role of the row's `group` (`all`), the roles of the named services (a service is the part of a role before its first `/`), or the roles carrying the named tags; a service row takes its services' group (services of two groups are 400), an `all` or `tag` row names `group` or belongs to the roles in no group. A topic is letters of any script (Korean included), digits, `.`, `_` and `-`, no spaces, up to 40 runes; a tag is a lower-case name (`[a-z0-9][a-z0-9._-]`, up to 40), since it is typed in `--scope tag:NAME`. A row's text may run to several lines (up to 4000 bytes): the first line is the summary and the rest its points; `rules list` prints the first line, `rules show N` the whole text. An admin (`/api/admin/rules…`) or a global boss (`/api/rules…`, `SWITCHBOARD_BOSS_ROLES`) reads everything and writes; any other role, a group's boss included, reads only its own group's rows in force whose scope reaches its base role (all, its service, one of its tags), each as `{"id","kind","text","topic"}` only, and gets 403 for `all=1`, the tags and every write, and 404 for a row outside its scope. `GET /api/rules[?service=S&topic=T&kind=K&all=1]` lists newest first (`{"rules":[…],"full"}`; `service` keeps the rows that reach the roles of S, `all=1` adds replaced and void rows); `GET /api/rules/{id}` adds, for a full reader, `history` (the rows it replaced and that replaced it, oldest first) and `answers` (the answered questions in `sources`, as decisions); `GET /api/rules/topics` is `{"topics":[{"name","active"}]}`. `POST /api/rules` with `{"kind","text","topic","new_topic"?,"scope","group"?,"sources"?:[question id…],"source_text"?,"replace"?:[id…],"alongside"?,"device"?,"match"?,"idempotency_key"?}` adds a row (201; a retry with the same key is the first row, 200): a source (answered question IDs, else 400, or a text) is required, an unknown topic needs `new_topic`, and when rows in force on the same topic and group share part of the scope (same scope kind; `all`, or a shared service or tag) it is 409 `{"error","rules":[…]}` until the writer replaces them (`replace`, rows in force in the same group, marked `replaced` in the same transaction) or stands alongside them (`alongside`; with both, only the `replace` rows are replaced and the others stay, as `rules edit` does). `POST /api/rules/{id}/void` takes a row in force out of force (409 otherwise). `device` names the mechanism that enforces a row (such a row never goes into sessions). `match` (`{"tool","command","path"}`, each optional, every one given must hold) is when a session hits the row: `tool` the tool name, exact or a pattern where `*` is any text (`mcp__*`); `command` a Go regular expression found in the command text; `path` a glob of the file path (`*` any text but `/`, `**` any text, `**/` also no directory, `?` one character but `/`); a regular expression that does not compile or a bad glob is 400. `GET /api/rules/mine` (any role, a global boss included, for its own role) is `{"rules":[{"id","kind","topic","summary","match"?}]}`: the rows in force reaching the caller's role, without a `device`, newest first, `summary` the text's first line; it sends an `ETag` and answers a matching `If-None-Match` with 304. `POST /api/rules/hits` with `{"ids":[…]}` (up to 100) counts one hit for each of the caller's `mine` rows named, ignores other numbers and repeats, and answers `{"counted":[…]}`; a full reader sees `hits` and `last_hit_at` on every row. The session hook's contract: [docs/rules-hints.md](docs/rules-hints.md). A boss role's directive (a new message, not a reply and not `no_reply`, from a global or group boss) ends with the recipient's rows in force that have no `device` and no `match`, after a `---` line: each decision as `결정 #N <topic>`, and the tips on one line, `요령 M줄 (주제: a, b) — switchboard rules list --kind tip`. It is part of the stored body, so an idempotent retry returns it as first sent; replies get none. `SWITCHBOARD_RULES_FOOTER=off` turns it off (default on). Tags: a service's tags (`PUT /api/rules/tags/services` `{"service","tags"}`, the whole set) are its roles' tags, and a role adds or removes its own (`POST /api/rules/tags/roles` `{"role","add"?,"remove"?,"inherit"?}`, inherit dropping the role's change); `GET /api/rules/tags` lists both, each role with the tags it ends with. A write publishes the `rules` change on the live bus. CLI: `switchboard rules [list] [--service S] [--topic T] [--kind decision|tip|all] [--all]` (decisions by default; tips with `--kind tip`, both with `--kind all` or `--all`), `rules show N`, `rules add --kind K --scope all|service:A[,B]|tag:X[,Y] --topic T [--new-topic] [--group G] --source ID[,ID]|TEXT [--replace N[,N]|--alongside] [--device NAME] [--idem KEY] TEXT` (on a 409 it prints the rows in force and the `--replace`/`--alongside` to add, exit 1), `rules edit N [TEXT] [--when-tool T] [--when-command RE] [--when-path GLOB] [--device NAME] [--source …]` (a new row replacing N with its kind, topic, scope, group, device, conditions and sources, changed by what is given; an empty `--when-*` clears that condition; `add` takes the same `--when-*`), `rules mine` (the caller's `mine` rows with their conditions), `rules hit N[,N]`, `rules void N`, `rules topics`, `rules tag list`, `rules tag set SERVICE TAG[,TAG]` and `rules tag role ROLE +TAG|-TAG|=TAG` (put `--` before a `-TAG`); each takes `--json` for the API JSON. Dashboard: 규칙 (응답 group) lists the rows with 결정 / 요령 / 전체 chips (결정 first), a service and a topic filter and 대체·무효 포함; each row shows its conditions and its hit count (걸림; the last hit on hover); a row's detail shows the text, scope, group, sources, conditions, hits, history and the answered questions, and for a row in force 고치기 (a new row replacing it, its conditions editable) and 무효로. 새 줄 adds a row, with optional conditions (도구, 명령 정규식, 경로 glob); a 409 lists the rows in force with 대체 and 나란히.
- **Rules ledger: proposals and answer classes.** (#409) Proposals: an admin or a global boss lets a role propose tips (`POST /api/rules/proposers` `{"role","on"}`, `GET` lists them as `{"proposers":[{"role","on","set_by","set_at"}]}`; `rules proposer [ROLE on|off]`); no role is taken for a proposer by its name or slot, and a group's boss writes nothing. A proposer's `POST /api/rules` takes `kind: tip` only (a decision is 403; `new_topic` is 400). Any other scope (tags, `all`, other services) is stored with `status: proposed` (`replace` and `alongside` are 400 then): it is in no `mine`, no directive footer and no limited reader's list or show, and each global boss gets one notice mail asking no reply (`[규칙 제안] #N <topic>`). Dashboard: the 규칙 tab's 제안 N toggle lists the proposals, a proposal's detail has 승인 (with 대체 and 나란히 on a 409) and 거절 with its reason, and 미분류 N shows the unclassified answers (per role on hover).
- **Mail-flow metrics.** `GET /api/metrics[?days=N]` (boss roles in `SWITCHBOARD_BOSS_ROLES` only, everyone else 403) and `GET /api/admin/metrics[?days=N]` (admin proxy only) answer the same JSON for the `N` days (1–90, default 7, else 400) ending now: `{"window":{"from","to","days"},"first_reply":{"count","answered","unanswered","p50_s","p90_s","max_s","buckets":[{"label","up_to_s","count"}],"by_recipient":[{"base",…same counts}]},"pending":[{"role","pending","oldest_s","over_threshold"}],"threads":{"multi_round","top":[{"thread_id","subject","parties","round_trips"}]},"sessions":{"by_role":[{"role","error_s","blocked_s","top_kinds":[{"state","seconds"}]}],"current":[{"role","state","since","seconds"}]},"thresholds":{"pending_s","error_s","blocked_s"}}`. **First reply** covers mail from a non-system sender that starts a thread (no `thread_id`/`reply_to` unless sent as a directive reply, and no `task_id` an earlier message in the window already carried); its latency is the time to the first later message, not from `switchboard/system`, sent by the recipient's base either in the same thread back to the sender's base, or to the sender's base or any boss role with the same non-empty `task_id` or with `#<id>` of the mail in its subject or body (any numbered slot counts for its base; progress open directives use the stricter reply rule above). Unanswered mail is counted but is no latency; percentiles are nearest-rank and `null` when nothing was answered; buckets are `<10m`, `<1h`, `<4h`, `<1d`, `>=1d`. **Pending** is the mail pending now per recipient role, without `switchboard/system` mail, oldest first. **Threads** counts, for each thread in the window, direction changes between its two most frequent bases (A→B→A→B is 3 changes); round trips = changes / 2 rounded down; `multi_round` is the number with ≥ 2 and `top` the 10 largest. **Sessions** is the time each numbered role spent in `error:*` / `blocked:*`, clipped to the window, with its 3 largest kinds, plus the online sessions in such a state now. Every state change is logged in `presence_log` (kept 60 days). Thresholds: `SWITCHBOARD_ALERT_PENDING` (default `2h`), `SWITCHBOARD_ALERT_ERROR` (`10m`), `SWITCHBOARD_ALERT_BLOCKED` (`30m`), Go durations, `0` disables. CLI: `switchboard metrics [--days N] [--json]` prints a compact summary. **Alerts:** the 30s sweep mails every boss role in `SWITCHBOARD_BOSS_ROLES` (normal priority, from `switchboard/system`) when a role has pending non-system mail older than the pending threshold (one alert per recipient role; a boss is not told about mail pending for its own base), or an online session has been in `error:*` / `blocked:*` longer than its threshold (one per session role). Each `(kind, role)` alerts at most once per UTC day. Subject `[지표] pending <role> 3통, 가장 오래 2h40m` or `[지표] error <role> <state>, 12m째`; the body of a pending alert lists the oldest five of that mail (`- #<id> <sender> — <subject>`, #354), and every body points to `switchboard metrics` and the dashboard `#metrics` tab; `task_id` is `alert:<kind>:<role>:<YYYY-MM-DD>`.

An `Idempotency-Key` header (up to 200 bytes; `permission request --idempotency-key KEY`) makes the request retry-safe per requester: the same key answers 200 with the first request and mails nobody again. The **parent** is the `parent` on the requester's active slot at request time and stays fixed on the request. Only a role in `SWITCHBOARD_BOSS_ROLES` (comma-separated bases or exact roles, empty by default) may answer; the requester's own base never may, even when it is a boss. The parent cannot answer: sessions on one machine can read each other's profile files, so only a boss, whose credential lives on a separate machine, is an independent check. A parent of the requester's own base (itself or a sibling slot) is ignored (`ignored_parent`), because any holder of the base token can act as every `<base>-N`. When no boss of another base is registered (or `SWITCHBOARD_BOSS_ROLES` is empty), the request is refused with 409 "nobody can answer", even when a parent exists, and the session falls back to its local prompt. The other 403 on the question endpoints (reading, answering or withdrawing a question the caller may not act on) is JSON too: `{"error":"not allowed to act on this question","code":"question_forbidden"}`. Ordinary questions omit `answerer`. Watchers from the asker's resolved settings (other bases only, unknown roles skipped) get a normal mail `[질문] <id> <asker> <first header>` with the questions and options, followed by a 「관련 지난 결정」 block when there are related decisions (below); bosses are not mailed and poll instead. These may come from other bases. `relay_to` (optional) names up to 8 addresses that also get the answer's text, for example `{"questions":[…],"relay_to":["team/boss","partner-a/dev"]}`: each must be an address send takes from the asker (a role, an alias or `<base>-N` within the asker's group reach; not `label:`), duplicates count once, and the asker itself may be named. Otherwise 400 naming the address (`relay_to: unknown role "x"`, `relay_to: "x" is outside your group`, `relay_to: at most 8 addresses (got N)`) and nothing is stored. The view carries `relay_to` (omitted when none) and the dashboard detail shows it as 중계.
  - `POST /api/questions/{id}/answer` with `{answers:[{selected:[label…],other?}]}`, one entry per question in order: labels must be options of that question, a single-select question takes at most one, `other` is up to 1000 bytes, and each entry needs a label or `other` (else 400). Only a boss of a base other than the asker's may answer, or, for an `answerer: owner` question, the asker's exact role (not another `<base>-N` slot, which is a different session), stored as `answered_by` = `panel` (else 403, unknown ID 404); the first answer wins and later ones get 409, as does an answer to a withdrawn question. 200 with the view. The asker gets a normal mail `[질문 답] <id> <first header>` (`task_id` = id; delivery below) with one line per question, `<header>: <question> = <labels>` plus ` / 기타: <other>`, then `답한 쪽: <role>`; watchers get the same text as `[질문 답] <id> <asker> <first header>`. Each `relay_to` mailbox gets, in the same transaction, one normal mail `[질문 답 원문] <id> <asker> <first header>` whose body is `질문: <id>`, `묻는 역할: <asker>`, `답한 곳: <answered_by>`, `답한 시각: <RFC 3339>`, a blank line, then the same answer text unchanged; not the asker's own mailbox, its answer mailbox or a watcher's (one mailbox never gets the answer twice), and its idempotency key `<id>:relay:<mailbox>` keeps it to one mail. With no live session there it waits in that inbox like any mail. A withdrawn question mails nobody. **Answer delivery.** A question asked from a live slot remembers that session (machine, directory, label). The answer goes to that session's live slot under whatever number it holds now; else to the most recently registered live slot of the asker's base with the same label (no label matches no label); else it is held (recipient `handoff:<id>`, status `held`, in no inbox) and the first session of the base that registers or heartbeats with that machine+directory or that label receives it, once, under a new ID. A directory and its session-marked form `<dir> #<8 hex digits>` on the same machine count as that machine+directory unless both carry different labels. While the slot that received the answer keeps its lease, the answer stays there; when that lease ends with the answer unread, the next register or heartbeat in the base holds it the same way (read answers stay). A session with another label never receives it. A question asked without a slot is answered at the asking address. While the answer is held the question view carries `"delivery":"waiting"` (the dashboard shows 전달 대기); otherwise `delivery` is omitted.
  - `POST /api/questions/{id}/withdraw`: only the asker's base (else 403); 409 when not pending; 200 with the view. No mail.

## Install and uninstall CLI

GitHub Actions builds versioned archives for Windows, Linux, and macOS (amd64 and arm64 where supported), plus SHA-256 checksums. Download the archive for your platform from Releases, verify `checksums.txt`, and place `switchboard`/`switchboard.exe` on PATH. The CLI does not update itself: `switchboard version --check` asks the server and prints `server vY, this vX`, plus `update: switchboard_<vY>_<os>_<arch>.tar.gz` (`.zip` on Windows) when this CLI is below the server's minimum (exit 3); exit 0 when current or a development build, exit 1 with one stderr line when the server cannot be reached. Configure the endpoint, role, and token as above. Config is stored at the OS user config directory under `switchboard/config.json` with user-only permissions. To uninstall, remove the binary and that config directory; removing config deletes the local token copy. Server messages remain until the operator removes the service volume.

### The agent plugin the CLI carries

The Claude Code plugin (question panel, mail delivery into the session, compact, the rules ledger hooks, presence, permission relay) lives in this repository, `internal/agent/claude/plugin/`, and ships inside the CLI binary (#477): its version is always the CLI's release tag, so there is nothing else to download.

- `switchboard plugin install` unpacks it to `<config dir>/plugins/claude/<version>/` (older version folders stay for sessions still holding them), registers `<config dir>/plugins/claude` as the local marketplace `switchboard`, installs and enables `switchboard@switchboard` at user scope, and disables (never uninstalls) a `switchboard` plugin from another marketplace: at user scope, and at a project's local or project scope where that project's settings turn it on. It uses Claude Code's own commands (`claude plugin marketplace add|update`, `claude plugin install|update|enable|disable --scope user`, `claude plugin list --json`; [CLI reference](https://code.claude.com/docs/en/plugins/cli-reference.md), [marketplaces](https://code.claude.com/docs/en/plugins/create-marketplace.md)) and never edits Claude Code's settings files itself. It prints one line saying what changed and in which settings folder (`CLAUDE_CONFIG_DIR`, else `~/.claude`). Without Claude Code on PATH it prints one line and succeeds.
- `switchboard plugin status [--json]`: the version this CLI installs, the installed one (`not installed` before the first install), whether it is enabled, the older copies (a switched-off local or project one is folded into one `N disabled old entries` line; `--json` lists every one), and a `sync:` line with the version in the marker and the last install tried (`[{"agent","available","where","want","installed","enabled","legacy":[{"id","scope","project","version","enabled"}],"sync":{"marked","last_attempt":{"version","at","ok","reason"}}}]`).
- On its own: `join` installs it after saving the profile, and the first run of a new CLI version installs it once before the command (the version whose install succeeded is in `<config dir>/plugin-version`; the same version reads only that file). That run prints only what changed or failed, on stderr (never on stdout, so `--json` output stays clean); a failure leaves the command running and is not marked: `<config dir>/plugin-attempt` keeps the last try, and the first run 10 minutes after a failed one tries again (`plugin install` retries at once). A machine without the agent counts as a success. `version`, `job` (the plugin's hooks run them under a short limit), `up`, `node`, `serve` and `admin` never install on their own; a node (`up`, `node`) brings it to its own version before it launches a hosted session of an agent that carries one, in the settings folder that session runs with (its `CLAUDE_CONFIG_DIR`, else `~/.claude`), once per version and settings folder; a failure is logged by the node and recorded as the session event `plugin-failed` with its reason (the dashboard's 기록: 플러그인 설치 실패), and the session launches anyway.
- Off: `--no-plugin` (before the command, or on `join`) or `SWITCHBOARD_PLUGIN=off` (also in a node's environment) stops the automatic installs; `plugin install` still installs when asked.

### Hosting: browser terminal access

```sh
SWITCHBOARD_HOSTING_TERMINAL=loopback   # default; or on, off
SWITCHBOARD_HOSTING_TERMINAL_ALLOW=198.51.100.0/24,2001:db8::/32   # optional
```

- `loopback`: the terminal's ticket and socket answer requests from a loopback peer without proxy forwarding headers; elsewhere 404.
- `on`: any listener and address, for a signed-in admin. The server refuses to start unless admin sign-in is set (`SWITCHBOARD_ADMIN_AUTH` builtin or oidc, or `SWITCHBOARD_ADMIN_PROXY_TOKEN`).
- `off`: 404 everywhere. It needs no admin sign-in; only `on` needs it set, or the server does not start.
- `SWITCHBOARD_HOSTING_TERMINAL_ALLOW`: when set, a client address outside the ranges gets 403. With `SWITCHBOARD_TRUST_FORWARDED=1` the client address is the one the nearest proxy forwarded, as for admin login.

The socket also checks `Origin` and takes a single-use ticket. Opening and closing a terminal socket is logged with the admin, time, view/input and client address (the dashboard's 기록 tab); typed text is not stored. Where the setting refuses, the dashboard's terminal screen shows why.

### Hosting: nodes on other machines

For nodes on other machines a hosting host can open a second listener besides `LISTEN_ADDR`:

```
SWITCHBOARD_HOSTING_REMOTE_LISTEN=100.64.0.10:8091            # IP:port; unset: no second listener leak-guard:allow
SWITCHBOARD_HOSTING_REMOTE_ALLOW=100.64.0.0/10                # CIDR list; unset: no address limit leak-guard:allow
```

A wildcard address (`0.0.0.0:<port>`, `[::]:<port>`, `:<port>`) is accepted, for a container that cannot know its outside address; the start log says "every interface" and the peer range (or any peer). The host refuses to start when the address is a host name or is loopback, or, with `SWITCHBOARD_HOSTING_REMOTE_ALLOW` set, is outside it. The remote listener serves the node channel (`/api/node/*`, node token) and the role API (role token), answers requests with `X-Forwarded-*` or `Forwarded` headers `403` (and, with `SWITCHBOARD_HOSTING_REMOTE_ALLOW` set, peers outside it), and answers the admin API, the dashboard, setup, sign-in and the browser terminal `404`. Where the browser terminal answers is `SWITCHBOARD_HOSTING_TERMINAL`'s (default `loopback`).

To attach a node on another machine:

1. On the host machine: `switchboard node invite pc2` (prints a one-time code).
2. On the node machine: `switchboard node --host http://100.64.0.10:8091 --join <code>`. <!-- leak-guard:allow -->

`node --host` accepts any http(s) URL; with `SWITCHBOARD_HOSTING_REMOTE_ALLOW` set on the node, only a loopback host or a host whose every address is inside it. The node's hosted sessions get that URL as `SWITCHBOARD_ENDPOINT`, so their mail goes through the remote listener. Each session also gets its own credential of its base role over the node channel: the node writes it as the profile `hosted-<record id>.json` in its config directory (user-only) and runs the session with `SWITCHBOARD_PROFILE` naming it (kept over a profile the folder's own agent settings name), so no profile or role token is copied to the node machine. The credential is refused once the record is removed, the node revoked or the role revoked; the role's own token is unchanged. `up`'s own node keeps the profiles its records name. Step by step, Windows and Linux: [docs/hosting-pc.md, Node on another machine](docs/hosting-pc.md#node-on-another-machine).

### Hosting: scheduled runs

A scheduled run launches a stopped hosted session at cron times (the host's time zone) and mails a prompt to the session's base role. It is written to the host's database, so `host auto` needs no server call; the host acts on its next sweep (30 s).

```
switchboard host stop <id>
switchboard host auto add <id> --cron '30 2 * * 1-5' --label nightly --prompt 'Work through queue.txt and report to team/boss.' --check 'grep . queue.txt' --notify team/boss --max-run 30m
switchboard host auto list
switchboard host auto run <auto-id>      # once, now
switchboard host auto show <auto-id>     # settings and newest runs (--runs N, --json)
switchboard host auto pause|resume|rm <auto-id>
```

`--check` is a precheck the session's node runs through the shell in the session's folder before each run (`--check-timeout`, default 60 s, at most 10 m). Its exit code decides:

| Precheck | Result | |
| --- | --- | --- |
| exit 0 | `fired` | launch (new conversation, or `--resume`) and mail; the precheck's output follows the prompt |
| exit 1 | `skipped` | nothing |
| other exit | `error` | nothing; alert |
| no exit within the limit | `timeout` | killed with everything it started; alert |

A node runs prechecks only when started with `--allow-checks` (`up`'s own node: `SWITCHBOARD_HOSTING_ALLOW_CHECKS=on`); otherwise the run ends `error`. Other results: `overrun` (the launched session ran past `--max-run`; it is stopped; alert), `busy`, `waiting`, `node-offline` (no alert). A session the run launched is stopped when the run's mail is completed or at `--max-run` (default 2 h). `error`, `timeout` and `overrun` alert once (Discord, and a system mail to the `--notify` roles); the next `fired` or `skipped` sends `resolved`. The dashboard shows the runs under the session (터미널 tab, 예약). Step by step, Windows and Linux, and moving an outside terminal automation (precheck plus a new session) to a scheduled run: [docs/hosting-pc.md, Scheduled runs](docs/hosting-pc.md#scheduled-runs).
